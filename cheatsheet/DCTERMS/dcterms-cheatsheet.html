01总览 · 描述资源的通用身份证 PART 1 · OVERVIEW

DCTERMS(Dublin Core Metadata Terms)是描述资源元数据的事实标准:文献、数据集、档案,「这东西叫什么、谁做的、何时发布、许可是什么」。命名空间 dcterms: = http://purl.org/dc/terms/。三层结构:

主线:几乎每个细化词都是老元素的 subPropertyOf——写细词,粗粒度查询自动命中,两端都省心。
本卡结构 = 本图:概览 → 三层词表 → 实操。
02定位 · DCMI 的三层词表 PART 1 · POSITION

现行为 DCMI Recommendation(2020-01-20),同时是 ISO 15836-1/-2。RDF 词表分布在四个命名空间,引用时认清:

命名空间装什么
purl.org/dc/terms/(dcterms:)主力:全部 15 老元素(2008 年镜像进来)+ 全部细化词 + 类与编码方案
purl.org/dc/elements/1.1/(dc11:)1990 年代末的 15 个老 URI,与新命名空间并存——别再新增引用
purl.org/dc/dcmitype/DCMI Type 词表:Collection、Dataset、Event、Image、Text…(资源的体裁分类)
purl.org/dc/dcam/DCAM 抽象模型词汇(描述词表本身的词)
老元素身世 1995 年俄亥俄州都柏林定了 15 个元素;2000 年开 /elements/1.1/ 命名空间;2008 年整套镜像进 /terms/——如今 dcterms:title 与 dc11:title 同义,新数据一律用 dcterms:。
0315 个老元素 · 分三组记 PART 2 · THE CLASSIC FIFTEEN

经典记法按「回答哪个问题」分三组:

组元素回答什么
内容title · subject · description · type · source · relation · coverage它是什么、讲什么、和谁有关
知识产权creator · publisher · contributor · rights谁写的、谁发的、谁出了力、权限归谁
实例date · format · identifier · language何时、什么形态、如何找到
KEY POINT 组别只是记忆术——15 个元素都是平铺的属性,没有形式化的分组公理;分组帮人选词,不帮机器推理。

04细化词 · 全是 subPropertyOf PART 2 · REFINEMENTS LAYER

细化词(refinements)让「宽词可选、细词可用」:每个细化词都是某个老元素的 subPropertyOf——写 dcterms:issued,查 dcterms:date 的人照样命中。

挂靠细化词(→ 都是左列的子属性)
dateissued · created · modified · valid · available · dateAccepted · dateCopyrighted · dateSubmitted
relationhasPart / isPartOf · hasVersion / isVersionOf · hasFormat / isFormatOf · references / isReferencedBy · replaces / isReplacedBy · requires / isRequiredBy · conformsTo
coveragespatial(空间覆盖)· temporal(时间覆盖)
descriptionabstract(摘要)· tableOfContents(目录)
title / identifier / format / rights / audiencealternative(副题)· bibliographicCitation(引文格式)· extent / medium(篇幅 / 载体)· accessRights / license(许可)· educationLevel / mediator(受众细化)
INVERSES · 逆对成对记 relation 家族的细化词几乎都成对:hasPart ↔ isPartOf、replaces ↔ isReplacedBy、requires ↔ isRequiredBy、references ↔ isReferencedBy、hasVersion ↔ isVersionOf、hasFormat ↔ isFormatOf。方向写反,含义就反——发布端选「从我这看出去」的方向,查询端两条都试。
05类与编码方案 · 取值的框 PART 2 · CLASSES & ENCODING SCHEMES

细化词的取值可以用类约束、用编码方案定格:

常用类 dcterms: 里的

  • Agent · AgentClass —— creator / contributor / publisher 的取值身份
  • LicenseDocument · RightsStatement —— license / rights 的取值
  • PeriodOfTime · Location · Jurisdiction —— temporal / spatial 的取值
  • ProvenanceStatement · Standard · Frequency · LinguisticSystem

编码方案 声明「值按什么规范写」

  • W3CDTF:ISO 8601 子集——「2026-10-15」「2026-10」「2026」皆合法,范围用「/」(端点可空)
  • ISO639-2 / RFC5646 —— 语言
  • URI / Point / Box / Period —— 标识与空间
取值形态 同一属性可挂字面量或资源:creator 既可写字符串字面量,也可指向一个 foaf:Person / dcterms:Agent——要可点、可合、可溯源,就写资源。
常用词 → 取值速查
属性取值写法配的类 / 方案
dcterms:creator / contributor资源 URI(人或机构)dcterms:Agent,可与 foaf:Person 对接
dcterms:issued / modified"2026-10-15" 字面量W3CDTF(ISO 8601 子集)
dcterms:license许可文档 URIdcterms:LicenseDocument(CC 等)

dcterms:spatial资源 URI(地点 / 辖区)dcterms:Location / Jurisdiction

dcterms:type体裁 URIdcmitype: Dataset / Text / Image…

07生态 · 谁在跟它配合 PART 3 · ECOSYSTEM
场景怎么配合
DCAT 数据集目录数据集的 title / publisher / issued / license / temporal 全套借用 dcterms——DCAT 管目录骨架,元数据槽位基本是 DCTERMS
PROV-O 溯源dcterms:creator / provenance 给顶层索引,细粒度生成链交给 prov:Entity / Activity——两套互不替代
Web 存档与图书馆OAI-PMH 收获、机构库存档、数码馆藏——老元素 15 项就是为它们设计的
schema.org 对接schema:name / schema:datePublished 等与 dcterms 大范围对齐——两套之间映射成本低
08实操坑清单 PART 4 · PITFALLS
  1. 新数据一律 dcterms:dc11: 老 URI 与 dcterms: 同义并存,但混引会让「同一属性两个名字」污染查询;存量数据迁移时做一次映射。
  2. 细化词写细不写粗:发布日期写 issued 而非 date——子属性语义更准,粗查询又不丢。
  3. relation 方向别写反:章节写 isPartOf 系列(指向整体);整书写 hasPart 系列(指向章节)——六个逆对全按「从我这看出去」选。
  4. date 家族按 W3CDTF 写:「2026」「2026-10」这种部分精度合法,别自己发明格式;范围用「2020/2024」。
  5. creator ≠ publisher ≠ contributor:创作、出版、贡献力量三选一,混写会让署名与引文系统归错人。
  6. license ⊑ rights:有具体许可写 license;accessRights 管访问权限(如「仅内网」),两者不是一回事。
  7. coverage 拆空间与时间:分别用 spatial / temporal,取值配 Location 或 PeriodOfTime,别把日期塞进 coverage。
  8. 体裁用 dcmitype:「这是数据集还是文本」写 dcmitype:Dataset / Text,与 dcterms:type 配合使用。
  9. source 与 references 别混:source 表「衍生自什么」(同时 ⊑ dc11:source 与 relation),references 表「引用了哪篇」——语义不同,选错方向元数据就失真。
