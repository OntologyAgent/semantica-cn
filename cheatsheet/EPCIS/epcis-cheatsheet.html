01总览 · 让伙伴共享「发生了什么」 PART 1 · OVERVIEW

EPCIS 是 GS1 的供应链可见性事件标准:贸易伙伴把「何物、何时、何地、何因」写成结构化事件互相共享。2.0 版(2022-06 与 CBV 2.0 同批批准)带来 JSON-LD 绑定与关联事件。

主线:每个事件都是一条可共享的业务事实——四维齐备,伙伴才能还原现场。
本卡结构 = 本图:概览 → 事件模型 → 标识与词表 → 示例与实操。
02定位 · GS1 的可见性层 PART 1 · POSITION

EPCIS 2.0 与 CBV 2.0 由 GS1 于 2022 年 6 月批准发布,演进自 EPCIS 1.x;JSON-LD 语法用官方 context(ref.gs1.org 的 epcis-context.jsonld)定义。它不规定系统怎么建,只规定事件怎么共享。

要点说明
只管事件语义库存系统、WMS 各建各的;跨组织交换的「发生了什么」用 EPCIS 表达
CBV 伴词Core Business Vocabulary:给 bizStep(业务步骤)、disposition(处置状态)等字段提供 GS1 共享取值——亦双标发布为 ISO/IEC 19988:2024(Edition 3)
自定义词CBV 没有的取值可以自定义——挂自己的命名空间,别混用 GS1 前缀
三语法同权XML(1.x 继承)· JSON · JSON-LD 表达同一事件模型,互转无损
03事件模型 · 四维与四类型 PART 2 · EVENT MODEL

每个事件回答四个问题——何物、何时、何地、何因:

维度字段内容
What 何物epcList · quantityList · childEPCs · input/outputEPCList事件涉及的对象(单品 / 批量 / 转换前后)
When 何时eventTime · eventTimeZoneOffset · recordTime业务发生时间(带时区)与系统记录时间——两者不同
Where 何地readPoint · bizLocation采集点(物理读取位置)与业务地点(业务归属位置)
Why 何因bizStep · disposition业务步骤(发货、验收…)与处置状态(在途、可售…)
四类事件 · 各管一种「发生了什么」
事件类型回答
ObjectEvent观测:对象在采集点被看到 / 状态改变(commissioned · observed · added · removed · decommissioned)
AggregationEvent物理装箱拆箱:对象加入 / 离开某个父层级(单品→箱→托盘)
TransformationEvent加工转换:输入对象变成输出对象(原料→成品、改包装)
AssociationEvent关联:对象与标识 / 固定位置建立或解除关联——不暗示物理包含

04标识与词表 · 事件的主角们 PART 2 · IDENTIFIERS & CBV

GS1 标识体系 对象的身份

  • GTIN 品类 · SGTIN 单品(序列化)
  • SSCC 物流单元(箱 / 托盘)
  • GLN 位置 · SGLN 序列化位置
  • 2.0 亦接受 GS1 Digital Link URI 与其他标识

CBV 共享词表 为什么这么做

  • bizStep:shipping · receiving · commissioning…
  • disposition:in_transit · sellable_not_accessible…
  • source / destination type:单据两端角色
个体 vs 批量 单品级用 SGTIN、批次级用 LGTIN 形态——同一 GTIN 的不同颗粒度,选错会让下游追踪断链。
05一条事件 · JSON-LD 示意 PART 2 · A WORKED EVENT
{ "type": "ObjectEvent", "action": "OBSERVE", "eventTime": "2026-10-15T09:00:00+08:00", "eventTimeZoneOffset": "+08:00", "bizStep": "cbv:bizstep-shipping", "disposition": "cbv:disp-in-transit", "epcList": ["urn:epc:id:sgtin:0614141.107346.2017"], "bizLocation": { "id": "urn:epc:id:sgln:0614141.00729.20" } }
读法 「09:00 在出货口读到这箱货,此后状态为在途」——一条事件就是一个业务事实;官方 epcis-context.jsonld 给出全部字段到词表的映射。
06实操坑清单 PART 4 · PITFALLS
  1. eventTime ≠ recordTime:前者是业务发生时间,后者是系统写入时间——补录历史事件时两者可以差很远。
  2. Association ≠ 装箱:关联事件(如传感器贴上箱体)不用 AggregationEvent——物理包含语义才归它。
  3. readPoint ≠ bizLocation:读卡器位置与业务归属位置是两个字段,混用会让追溯报告错位。
  4. 自定义词挂自己的命名空间:CBV 取值不够用时自建 bizStep,别把自造词塞进 GS1 前缀。
  5. 修正历史不删事件:错误用 errorDeclaration 声明,原事件保留——审计链就是事件链。
  6. 单品 / 批次选对颗粒:SGTIN(单品)与 LGTIN(批次)混用会让「这一件」的追踪断掉。
  7. JSON-LD 用官方 context:epcis-context.jsonld 定义字段到词表的映射——自造 context 会破坏互换。
  8. 1.x → 2.0 平滑:XML 绑定仍在;新系统直接选 JSON-LD,老系统按节奏迁。
