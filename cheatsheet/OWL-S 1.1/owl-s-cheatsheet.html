01总览 · 一个服务,三份档案 PART 1 · OVERVIEW

OWL-S 用一份本体描述服务:Profile 负责被发现,ProcessModel 负责被理解,Grounding 负责被执行。先看三个问题怎么分给三份档案,再逐层拆。

主线:发现看 Profile,编排看 Process,调用看 Grounding——三份档案各答一个问题。
过程模型是重心:IOPE 四大件 + 九件控制构造,撑起全部流程表达。
本卡结构 = 本图:概览 → 三档案 → 过程模型细节 → 落地与遗产。
02定位 · 让机器看懂「服务」 PART 1 · POSITION

OWL-S(Semantic Markup for Web Services,前身 DAML-S)用本体给 Web 服务写三份「档案」:能干什么、怎么运转、怎么调用——让服务发现、编排、调用全部自动化。它是后来一切语义服务描述的思想源头。

STATUS · 身份先看清 OWL-S 1.1,W3C Member Submission 2004-11-22(法国电信、马里兰大学 MIND 实验室、NIST、斯坦福等九家联合提交)——不是 W3C Recommendation。规范文本位于 w3.org/Submission/,发布即定稿,此后没有 W3C 主导的后续版本。
上层模块回答的问题用途
ServiceProfile这个服务能提供什么?广告与发现
ServiceModel它怎么运转?过程建模、编排、仿真
ServiceGrounding怎么跟它交互?协议、消息格式、序列化
03Service · 一个服务,三份档案 PART 1 · THE TOP CLASS
Service 是枢纽类:每个已发布服务一个实例,经 presents / describedBy / supports 挂上三份档案;profile 侧有反向属性 presentedBy。
基数规矩:模型至多一个;grounding 必须唯一归属;profile 和 grounding 数量上不封顶。

04Profile · 给服务写「招聘启事」 PART 2 · PROFILE
描述块内容
提供方信息联系人、服务名、联系方式
功能描述IOPE:Inputs / Outputs / Preconditions / Effects——发现与匹配的核心
属性serviceParameter(技术参数)· serviceCategory · serviceClassification(挂 UNSPSC 等分类)· serviceProduct
分类字段categoryName · taxonomy · value · code
匹配怎么发生 发现引擎比对「请求的 IOPE」与「广告的 IOPE」:输入类型可供给、输出类型是子集、前置条件可满足、效果可接受——四级过滤,从粗到细。
05Process 三兄弟 · 过程模型的骨架 PART 2 · PROCESS MODEL
类性质关系
AtomicProcess单步、可直接调用、必须有 groundingSimple 的 realizedBy
SimpleProcess抽象描述,不可调用、无 groundingexpandsTo 展开 → Composite;realizedBy 落地 → Atomic
CompositeProcess由控制构造组装的复合流程恰好一个 composedOf(range ControlConstruct)
Perform 与 Produce 复合流程里的每一步是 Perform 实例(调用某个原子/简单过程);Produce 负责在流程中途向复合过程「发」输出。步骤之间怎么传值,见 §09 的 Binding。
06IOPE · 服务描述的四大件 PART 2 · IOPE
件属性含义
InputhasInput调用前必须给的东西
OutputhasOutput服务产出的东西
PreconditionhasPrecondition调用成立的先决条件(如「信用卡有效」)
EffecthasResult执行后世界状态的改变(如「订单已创建」)

参数类 Parameter

  • Parameter ⊑ swrl:Variable(直接挂上规则语言)
  • 四子类两两不相交:Input / Output / Local / ResultVar
  • 类型经 parameterType(至少一条 IRI)

Result 的细化 conditional

  • inCondition:在什么条件下
  • withOutput / hasEffect:有何输出与效果
  • 「条件结果」——同一个服务,不同情形不同后效
07控制构造 · 流程编排九件套 PART 2 · CONTROL CONSTRUCTS
构造语义
Sequence顺序执行
Split并发全开,不等彼此
Split-Join并发 + 屏障同步(全部完成才继续)
Any-Order都要执行,顺序随意
Choice多选一执行
If-Then-ElseifCondition / then / else
Iterate抽象迭代(不落地)
Repeat-While / Repeat-Until条件循环(whileCondition / untilCondition + 循环体)
表达式哪来 条件与效果是 Expression(expressionLanguage + expressionBody):KIF/PDDL 用字符串字面量,SWRL/RDF/DRS 用 XML 字面量——语言开放,塞什么逻辑随你。

08Grounding · 从本体落到 WSDL PART 3 · GROUNDING

OWL-S 1.1 的 grounding 以 WSDL 1.1 为落点:抽象过程映射到具体操作。

OWL-S 侧WSDL 侧
AtomicProcessoperation(request-response / one-way / notification;复合过程另用 solicit-response)
Input / Outputmessage parts
OWL 类型abstract types
扩展点 WSDL 侧用 owl-s-parameter 与 owl-s-process 两个扩展属性回指 OWL-S 实体——双向导航,机器可沿任一侧进入另一侧。
09数据流 · 步骤之间怎么传值 PART 3 · DATAFLOW
# Perform 的输入来自哪里:hasDataFrom → Binding Binding( toParam: 目标参数 valueSource: ValueOf( theVar: 上一步Perform / TheParentPerform ) ) # 或直接给常量:valueData / 声明类型:valueType / 函数加工:valueFunction # 特殊变量 TheParentPerform:指向「整个复合过程」的 Perform,取全局参数用

取值来源 valueSource

  • 前一步 Perform 的输出(ValueOf + fromProcess)
  • 复合过程自身的参数(TheParentPerform)
  • 常量 valueData

本地变量 Local

  • 过程中间态存 Local 参数
  • 与 Input/Output/ResultVar 互不相交
  • 流程内部的「草稿纸」
10遗产与现状 · 读完 OWL-S 再看今天 PART 3 · LEGACY & TODAY
  1. OWL-S 是 Member Submission,2004 年后 W3C 层面没有续作——新项目不要直接落地它,读它为了懂问题。
  2. 它的三段式(Profile/Model/Grounding)思想活在今天的 OpenAPI/OpenAPI+ Linked Data 混合方案、WSMO 与 microservices 契约里。
  3. IOPE 四件套仍是服务语义描述的最佳词汇表——任何服务目录设计都值得抄这份结构。
  4. 要自动化服务发现,现代实践多以知识图谱存服务元数据(RDF 描述加 SKOS 分类),协议层交给 OpenAPI。
  5. 历史本体文件在 daml.org/services/owl-s/,引用时用 Submission 版 IRI,别链接失效镜像。
