## 一、概览

### 1.1 背景与目的

RDF(Resource Description Framework,资源描述框架)是万维网上的最小数据模型:**一切皆三元组**。

它解决的问题:让不同系统、不同组织的数据能互相引用、互相拼接。任何一张图都能引用任何人发的 IRI——不需要 schema 协商,不需要改表。这条约束换来无限的可拼接性,是整个语义网技术栈的地基。

1.1 版把原本分散的文档族整成一套同日发布的推荐标准:

| 文档 | 管什么 |
|---|---|
| Concepts & Abstract Syntax | 数据模型:三元组、图、术语、数据集(核心规范) |
| Turtle / N-Triples / TriG / N-Quads | 文本语法家族 |
| XML Syntax | XML 交换语法 |
| JSON-LD | 给 Web API 的 JSON 语法 |
| Semantics | 模型论语义与推理规则 |
| RDF Schema 1.1 | 类与属性的词汇(rdfs:,见 PL.02) |

全家族于 2014-02-25 同日成为 W3C Recommendation。1.1 相对 1.0 的三件大事:**UTF-8 一统天下**(不再 ASCII/latin1)、**Turtle、N-Triples 升为正式推荐标准**、**数据集(多图)写进核心规范**。所有文档共用一个抽象语法,互转无损。

### 1.2 整体定义

从最小的单元往上搭:

- **三元组(triple)** = 主语 + 谓语 + 宾语,是最小的「句子」。任何复杂结构都能拆成一袋句子。
- **图(graph)** = 三元组的**集合**。是集合不是列表——重复三元组自动去重;图的真值只取决于它包含哪些三元组,与书写顺序无关。图与图之间没有主从,只有包含(A 的图可以是 B 的子图)。
- **数据集(dataset)** = 恰一个默认图 + 若干「(图名, 图)」对,多图打包的形态。

三元组三个位置各有准入门槛,能出现的绿灯只有三种,合称 **RDF 术语(RDF terms)**:

```
主语:IRI ∨ bnode        谓语:IRI(仅此一种)        宾语:IRI ∨ 字面量 ∨ bnode
```

谓语位置只允许 IRI——谓语本身就是需要被定义、被复用的词汇,这也是词表(vocabulary)存在的意义。规范明说三种术语「彼此不同且可区分」。

### 1.3 表达方式一览

一套模型,多串语法。同一张图可以用任何一种语法写出来,彼此可互转:

- **Turtle**(text/turtle)——人写、人读、版本管理的主力语法
- **N-Triples**(application/n-triples)——逐行三元组,机器友好,流式处理
- **TriG / N-Quads**——Turtle / N-Triples 的数据集扩展(带命名图)
- **RDF/XML**(application/rdf+xml)——老牌 XML 交换语法,遗留系统对接
- **JSON-LD**(application/ld+json)——JSON 文档 + `@context` 映射成图,给 Web API 和前端

### 1.4 整体结构关系

一张图看全 RDF 1.1 的四个层面,从里到外、从简单到复杂:

```
RDF 1.1 = 一套数据模型 + 一组序列化语法 + 一层形式语义
│
├─ 词汇(三元组的零件)────────────────────── 「点」层
│    IRI      全局唯一的名字(见 2.1)
│    字面量   写进句子的值(见 2.3)
│    bnode    没有名字的节点(见 2.2)
│
├─ 数据模型(抽象语法,全世界只有一份)────── 「图」层
│    triple  = 主语 · 谓语 · 宾语              ← 最小单元,一个「句子」
│    graph   = 三元组的集合                    ← 去重、无序
│    dataset = 默认图 + (图名, 图)对           ← 多图打包
│
├─ 序列化语法(同一张图的多种写法)────────── 「文件」层
│    Turtle / N-Triples / TriG / N-Quads / RDF/XML / JSON-LD
│
└─ 语义(从图里能必然推出什么)────────────── 「推理」层
     简单蕴含 → RDF 蕴含 → RDFS 蕴含 →(OWL 在 PL.04)
```

**文件层与图层的关系**是理解全部细节的钥匙:

- 文件层允许偷懒:相对 IRI、前缀缩写、`a` 代替 `rdf:type`……这些全是糖
- 解析器读文件,把糖展开,补全 IRI,然后建图
- 进到图层那一刻,只剩绝对 IRI、字面量和不具名的 bnode——糖不存在于图层

后面每个概念的细节,都在这条「文件 → 图」的流水线上各就各位。

## 二、概念细节

### 2.1 IRI

**IRI(Internationalized Resource Identifier,国际化资源标识符)就是一个字符串**,长得像网址:

```
http://xmlns.com/foaf/0.1/Person          ← foaf 词表的「人」这个类
http://www.w3.org/2004/02/skos/core#Concept
http://dbpedia.org/resource/北京           ← IRI 允许非 ASCII 字符
urn:isbn:0451450523                        ← 连 http 都可以没有
```

拿 `https://investment.example/ontology/Company` 拆开:

| 部分 | 值 |
|---|---|
| scheme | `https` |
| authority(站点) | `investment.example` |
| path | `/ontology/Company` |
| 可选 fragment(`#` 后面) | 如 `#Concept` |

和相近概念拆差别:URL 是「地址」,告诉你去哪取东西;IRI 是「名字」,只负责唯一标识,不保证能访问。URI 是两者的统称,IRI 是 URI 的超集——多允许了中文等 Unicode 字符。RDF 图里所有类、属性、实体,都用 IRI 当名字。

常见误解:以为 IRI 必须能打开、必须指向真网页。不是。它只是名字,访问了什么都不返回也完全合法。「造一个能解引用的 IRI」是良好实践,不是要求。

#### 为什么「抽象语法里必须绝对」

绝对 = 名字自带全称,不依赖上下文。`ontology/Company` 是相对的,`https://investment.example/ontology/Company` 是绝对的。

为什么必须绝对?RDF 图是数据,会被复制、合并、搬进各种存储。名字一旦依赖「我在哪个文件里」,搬到别处含义就变了,两张图合并时同一个东西会裂成两个。RDF 的野心是一张全球数据空间,所以名字必须放之四海皆准。

#### 「相对 IRI 只是糖」是什么意思

先解释糖(syntactic sugar):一种偷懒的缩写写法,机器展开后和手写全称一字不差,不产生任何新东西,只是让打字的人省力。

下面三种写法,产出的 RDF 图完全一样:

```turtle
# 写法 A:老实写全名
<https://investment.example/ontology/Company> a owl:Class .

# 写法 B:前缀缩写(另一颗糖)
@prefix ex: <https://investment.example/ontology/> .
ex:Company a owl:Class .

# 写法 C:相对 IRI + base
@base <https://investment.example/> .
<ontology/Company> a owl:Class .
```

写法 C 少打了域名那截,机器的处理就一步字符串拼接:拿 base 补全成全名,补完才入库。所以:

- **文件这一层**:允许偷懒写短名(糖)
- **图这一层**:永远是全名(所以抽象语法里必须绝对)

网页里你早就在用同一机制:HTML 写 `<img src="logo.png">`,浏览器按当前页面地址补全成完整 URL 才去下载。相对 IRI 就是一回事:你写短的,工具帮你拼长的,最终存下来的只有长的。

顺带分清:`ex:Company` 这种前缀缩写也是糖,但是另一颗——前缀本身是绝对的,拼出来仍是绝对 IRI,不算相对。

#### 相等 = 简单字符串比较

两个 IRI 相等,当且仅当字符串一个字符不差。`http://example.com/a` 和 `http://example.com:80/a` 在 Web 服务器眼里是同一个网站,在 RDF 里是两个不同的名字。

为什么这么死板?如果允许系统「聪明地」规范化,各家实现聪明得不一样,同一个名字会错误合并或错误分裂。标准把责任推给造名字的人:造的时候就造规范形(见下),比较的机器逐字符傻比,换来全世界的实现结果一致。

#### fragment(`#Concept`)是什么

看这个 IRI 的两截:

```
http://www.w3.org/2004/02/skos/core#Concept
└──────── 第一截 ────────┘└第二截┘
        一个文档的地址      文档里的一个词条名
```

网页里天天见 `#`:点「跳转到本页某节」,URL 变成 `page.html#section2`。`#` 后面那段叫 fragment(片段),作用是「这份文档内部的位置」,浏览器自己处理,不会发给服务器。

RDF 词表借用这个机制:W3C 发一份 SKOS 词表,本质是一个文档,地址是 `http://www.w3.org/2004/02/skos/core`。文档里定义了几十个词条(Concept、prefLabel、broader……),每个词条的名字就是拼上 `#词条名`。类比:`#` 前面是楼(文档),`#` 后面是门牌(词条)。

「可选」的意思:IRI 带 `#xxx` 也合法,不带也合法。带上之后就是另一个名字——按逐字符比较,`https://ex.com/doc` 和 `https://ex.com/doc#thing` 是两个不同的 IRI。

#### 规范形:众多写法里选定的那一个标准答案

canonical form(规范形)= 同一个东西的多种等价写法里,被钦定为标准的那一种。规范化(normalization)则是「把别的写法改写成规范形」这个动作。

日期你天天见:`2026-10-15`、`2026/10/15`、`15/10/2026` 说的是同一天,ISO 8601 钦定了 `2026-10-15`。数据库里存它、程序里比它,都用这一种写法。

放在 IRI 上。同一网站的多种写法:

```
http://example.com:80/a     ← 端口 80 是 http 默认,可省
HTTP://EXAMPLE.COM/a        ← scheme 和主机不分大小写
http://example.com/./a      ← /./ 纯属多余
```

Web 服务器眼里这是一个地址;逐字符比较眼里这是三个不同的 IRI。RDF 偏偏选了逐字符比较——那「相同」就不能靠比较时动脑子,只能靠写的时候就写成同一个样子。这个「同一个样子」就是规范形:

- scheme 和主机小写
- 省略默认端口 `:80`
- 路径消掉 `/./`、`/../`
- 百分号编码用大写十六进制
- Unicode 用 NFC 形态

整件事的逻辑:**比较一方装傻(逐字符)+ 造名一方尽责(只造规范形)**,两头配合,全世界的系统才能对同一个名字得出同一个判断。速查卡「IRI 相等的坑」末尾的建议清单,就是「造 IRI 时走规范形」的操作手册(另见 3.2)。

### 2.2 空白节点(bnode)

**blank node(空白节点)= 图里一个没有 IRI 的节点**。它能连线、能带属性,就是没上户口:

```turtle
_:b1 foaf:name "张三" ;
     foaf:knows _:b2 .
_:b2 foaf:name "李四" .
```

`_:b1` 这个标签只在当前文件里有效。另一个文件也写 `_:b1`?那是完全不相干的另一个东西——标签像审讯室里给嫌疑人贴的「甲、乙」,换一个房间重新编号。Turtle 里还有匿名写法 `[ foaf:name "Bob" ]`,方括号内直接挂属性,节点本身不命名。

两个典型场景:

- **装复合值**:想写「王五的地址是(中山路 1 号,北京)」。地址这个结构本身不需要全球身份,只是王五的一个属性值——用 bnode 装,不用费心造 IRI。
- **身份不明**:「某位审查者批准了这个稿子」——确实有这么个人,但指认不出来。

对照 IRI:IRI 是身份证号,bnode 是匿名路人。你只能说「有这么个人,他做了这些事」,没法在图外叫他——这就是「只为『存在』而存在」。标签属于文档局部作用域,不持久、不可移植,不属于抽象语法。

由此带来:两张图的 bnode 不能按名字对齐,「同一张图」的判据只能靠同构配对(见 2.4)。

#### Skolem 化:给匿名节点上户口

Skolemization = 把 bnode 换成一个专属的、全球唯一的 IRI。匿名路人办了身份证。

名字来自逻辑学家 Skolem:数理逻辑里把「存在某个 x」改写成具体常量,RDF 借了这个词。操作就一步替换:

```turtle
# 之前
_:b1 foaf:name "张三" .

# Skolem 化后
<https://example.com/.well-known/genid/d8f2c1> foaf:name "张三" .
```

`/.well-known/genid/` 是规范建议的固定路径(也有用 `urn:uuid:` 的),作用是挂牌子:这是系统生成的占位号,不是真实资产的地址——别看它长得像 IRI 就去访问,也别当成「张三有个正式主页」。换完之后,跨文档引用、去重、图合并都有据可依。

什么时候非做不可?跨文档引用的时候。文件 A 里有个 bnode,文件 B 想说「就是 A 里那个匿名节点」——说不出来,标签不出文档就作废。唯一的办法是先在 A 里给它上户口,B 再引用这个号。同理,SPARQL 1.1 只认 IRI 当图名,想交换带 bnode 图名的数据集,先 Skolem 化。

代价:上完户口,「这是个匿名节点」这层信息丢了。所以实践纪律是——需要跨文档指认的,一开始就造正经 IRI;bnode 留给真不在乎身份的东西。

### 2.3 字面量

**字面量 = (词法形式, 数据类型 IRI, 语言标签?)**,是写进句子的「值」:

```turtle
"42"^^xsd:integer
└┬┘└────┬────┘
词法形式   数据类型
(写出来的字符串)  (这写法该怎么理解)
```

- **词法形式(lexical form)**:字面量的字符串本体,「写出来的样子」。这里就是字符序列 `4` `2`。
- **数据类型 IRI**:声明这串字符要按什么规则读。`xsd:integer` 说:这是整数。
- **语言标签**(可选):如 `"猫"@zh-CN`,只允许配 `rdf:langString` 一个类型,且必须非空、符合 BCP 47。

三种形态:

| 形态 | 构成 | 示例 |
|---|---|---|
| 简单字面量 | 无标签无类型,就是 xsd:string | `"abc"` |
| 语言标注串 | 语言标签 + rdf:langString | `"猫"@zh-CN` |
| 类型化字面量 | datatype IRI 指定值空间 | `"42"^^xsd:integer` |

#### 两种相等:词项相等 ≠ 值相等

- **词项相等(term equality)**:三成分逐字符一致。
- **值相等(value equality)**:经「词法 → 值」映射后,落在值空间同一点。

`"1"^^xsd:integer` 与 `"01"^^xsd:integer` 词项不同(写法不一样),值相同(都是数字 1)。查询里的 FILTER 用值比较,去重合并用词项比较——混用是经典 bug 源。

#### 词法空间与值空间

每个类型都自带两张清单:

- **词法空间(lexical space)**:哪些字符串算是它的合法**写法**。`xsd:integer` 认 `"0"`、`"42"`、`"-7"`、`"007"` 这样的串;`"三十"`、`"4.5"`、`"hello"` 都不在清单里。
- **值空间(value space)**:类型规定的实际**值**的集合。`"42"` 和 `"042"` 是两个词法,对应值空间里同一个数字 42。

词法空间管「怎么写」,值空间管「是什么」。

#### 病态字面量:写法不在清单里

ill-typed literal(病态字面量)= 词法形式不在类型的词法空间里,也就是「声明是整数,写法却不是整数的合法写法」:

```turtle
ex:问卷1 ex:年龄 "三十"^^xsd:integer .
```

`"三十"` 这串字符不在 `xsd:integer` 的合法写法清单里——这就是病态。速查卡那句话「图合法、语义不一致;实现必须照单全收」,三段拆开:

**「图合法」**——解析器不报错。Turtle 语法只要求 `^^` 后面跟一个 IRI,至于那个 IRI 说的类型和前面字符串配不配,语法不管。这张图是正经 RDF,能解析、能入库、能查出来。

**「语义不一致」**——但按 Semantics 的推理语义,这行字自相矛盾:它声称一个东西是整数,词法却不是任何整数的写法。推理器接管后,这会让整张图逻辑上站不住。

**「必须照单全收,不许悄悄改写」**——RDF 的立场:存储层禁止「好心」拒绝它、纠正它、或把它转成别的形式。数据在系统之间必须原样搬运。

为什么选「照单全收」?RDF 是**交换格式**,不是数据库表结构。如果解析器各自「聪明地」拒收或纠正,同一份数据在 A 系统能入库、在 B 系统被改写,对账就毁了——和 IRI 相等那条是同一个设计哲学:**机械的部分绝不含糊,判断的部分交给专门的层**。最贴近的体验是 Excel:单元格格式声明是数字,你偏输入「三十」,Excel 照样让你存;哪天拿这列求和,才炸出 `#VALUE!`。

实践中谁管它:入库照收,SPARQL 照查;SHACL 的 `sh:datatype` 约束会把它揪出来;拿它做算术或推理时问题才暴露。纪律:**数据入口处用形状校验把关,别指望存储层替你拦**。

#### 非规范类型,一句带过

`rdf:HTML`、`rdf:XMLLiteral` 的值是解析后的 DOM 片段,不保证所有实现都认,交换场景慎用。

### 2.4 图

前面三个概念是「点」,这里开始组装。

#### 三元组与图

一条三元组就是一个「句子」;一张图是一袋句子。图是**集合**:重复三元组自动去重,真值只取决于包含哪些三元组,与书写顺序无关。

#### 图同构:怎么判断两张图是同一张

IRI 和字面量有名字,直接原样比对;bnode 没名字,只能靠**试配对**。两份导出文件,内容是同一张图,只是匿名节点换了代号:

```turtle
# 旧导出 G1                # 新导出 G2
_:a1 foaf:name "张三" .     _:p foaf:name "张三" .
_:a1 foaf:knows _:a2 .     _:p foaf:knows _:q .
_:a2 foaf:name "李四" .     _:q foaf:name "李四" .
```

代号是每个文件自己编的,`a1` 和 `p` 没法直接比。办法:**把 G1 的代号按某种配法换成 G2 的代号,看换完之后两份文件是否逐行一模一样。**

G1 有两个匿名节点,配法一共两种,全试一遍:

**配法甲:a1→p, a2→q。** 替换后 G1 变成:

```turtle
_:p foaf:name "张三" .
_:p foaf:knows _:q .
_:q foaf:name "李四" .
```

和 G2 逐行对照——一字不差。✓ 这张配法成了。

**配法乙:a1→q, a2→p。** 替换后 G1 里叫「张三」的成了 q,和 G2 对不上。✗

结论:恰好存在一种配法能换到完全重合,所以两份是同一张图。这个能成立的配法就是**双射**;两种配法全失败,才判「不是同一张」。一句话:**双射就是「一种能过检查的名字替换方案」**。这就是图同构——「同一张图」的判据。

**双射(bijection)展开讲**:一张双向都能查、查了唯一的对照表。用反例理解:英汉字典里 bank 对应「银行」和「河岸」——正查出现两个答案;「银行」翻回去又定不下来是哪个英文。这种映射丢信息。双射是完美的字典:正查唯一、反查唯一、每个词都收录,来回翻译一个字不丢。它就是「无损」二字的数学化:两边信息量刚好相等,互相能完整还原。

双射的三个实际用途:

1. **对账**:两份数据是不是同一份?数据迁移后的新旧库对账、图同构判定、git 合并时两边改动是不是同一处——本质都是在找那张能过检查的配对表。
2. **可逆转换**:Base64、加密、压缩、序列化,凡宣称「无损」的转换,数学保证都是双射。Base64 任意 3 字节 ↔ 恰好 4 个字符,唯一对应,所以能解回原文。有损压缩(如 JPEG)故意放弃双射——回不去了,换来体积暴减。
3. **ID 系统的设计目标**:身份证号一人一号绝不重号,就是要跟「人」构成双射。图库里的 IRI 设计追求的也是这个。

数学里把「本质相同,只是叫法不同」正式化,用的就是双射。判断「这两个东西是不是一回事」时,做的就是在找双射。顺带一提,同构判定是「试配对」,出了名的费劲,图大了会变慢。

#### 图合并

多图并成一张 = 三元组集合并集。注意:**同名 bnode 在合并后视为同一节点**——两个文件都写 `_:b1`,合并后就是一个节点。合并前想清楚 bnode 归属,别让不相干的匿名节点意外合体。

#### 数据集:默认图与命名图

dataset = 恰一个**默认图**(唯一、无名、允许为空,是 SPARQL 查询的起点)+ 若干「(图名, 图)」对。

- 三元组自己不分家,分家靠装进哪个图。
- bnode 可以**横跨多张图**共享。
- 图名「不要求指称那张图」——配对是语法行为,不是语义命名。别把「图 IRI」当资源描述的主语,除非另外声明它指什么。
- 规范允许 bnode 当图名,但 SPARQL 1.1 只认 IRI;跨系统交换带 bnode 图名的数据集,先 Skolem 化。
- 规范**刻意不定义**命名图的形式语义(只给了语法)——想在语义层面用命名图,先查工具的行为。

### 2.5 语义与推理

#### 蕴含是什么

entailment(蕴含)=「只要 A 为真,B 就假不了」。B 的内容本来藏在 A 里,推出它不需要任何新知识,纯机械操作。

关键区别:**蕴含 ≠ 图里真的存了那条三元组**。RDF 图是「一袋句子」,蕴含回答的是:这袋句子必然还成立哪些句子。你的图「实际上说出口的话」,永远比它存盘的三元组多——蕴含就是把这些没写出来的话找出来。

规范把推理分成三档楼梯,一档比一档推得远:

#### 第一档:简单蕴含——白纸黑字抄出来的

最弱的推理:子图。你写了三条三元组,那其中任何一条都被你的图蕴含——它本来就是子集。形式化一点:G 蕴含 H ≈ H 的某个同构是 G 的子图。不碰任何词表含义,纯集合包含,bnode 的对齐靠同构。

#### 第二档:RDF 蕴含——承认字典自带的几句话

一句话:**推理时,除了你的图,还允许把「RDF 官方词典」里印死的几句话拿来用。**

规范自己也要用词:`rdf:type`、`rdf:_1` 这些是 RDF 发明的词,规范得说清这些词自己是什么身份——而且说的方式还是三元组,保证永远为真。这种印死在规范里、不用证明、任何图都免费附带的句子叫公理(axiom)。真的就长这样:

```turtle
rdf:type  rdf:type  rdf:Property .                      # 「rdf:type」这个词,是个属性
rdf:_1    rdf:type  rdfs:ContainerMembershipProperty .  # 「rdf:_1」是容器成员属性
```

注意第一行多别扭:句子在谈论 rdf:type 自己。规范没法用别的格式写「词是什么」,因为 RDF 只有三元组这一种格式——词典也只能用词条的格式印。

对照一遍就懂。你的图只有一行:

```turtle
ex:清单 rdf:_1 ex:苹果 .
```

问:你的图蕴含「rdf:_1 是容器成员属性」吗?

| 档位 | 答案 | 为什么 |
|---|---|---|
| 简单蕴含 | 否 | 这句话不在你的图里,也不是它的子图 |
| RDF 蕴含 | 是 | 这是公理,规范白送,哪怕你的图是空的也送 |

为什么存在感低:公理全在谈论 rdf: 这些词自己,没有一个跟你图里的业务数据(旺财、苹果、张三)挂钩。只有当你问「rdf:_1 是什么来头」这种元问题时才用得上。真正把你的数据串起来推理的,是第三档。

#### 第三档:RDFS 蕴含——词表法典生效

这才是真正干活的推理。加载 `rdfs:` 词表语义,主要四个开关:

```turtle
# ① subClassOf(类层级):「狗是动物」
ex:狗 rdfs:subClassOf ex:动物 .
ex:旺财 rdf:type ex:狗 .
# ⇒ 免费得到:ex:旺财 rdf:type ex:动物 .

# ② subPropertyOf(属性层级):「生育属于亲代关系」
ex:生育 rdfs:subPropertyOf ex:是亲代 .
ex:旺财爹 ex:生育 ex:旺财 .
# ⇒ 免费得到:ex:旺财爹 ex:是亲代 ex:旺财 .

# ③ domain(定义域):用了这个属性,主语必属于某类
ex:作者 rdfs:domain ex:人类 .
ex:张三 ex:作者 ex:书一 .
# ⇒ 免费得到:ex:张三 rdf:type ex:人类 .

# ④ range(值域):宾语必属于某类
ex:作者 rdfs:range ex:书 .
# ⇒ 免费得到:ex:书一 rdf:type ex:书 .
```

实际用途:最常见的是查询扩展。问「所有动物」时,狗的实例自动出来,不用给每个实体重复标注类层级。落地两种做法:物化(把推出来的三元组真写进库里)或查询时展开(查询器临时按规则推)。Semantica 的 `reasoning` 模块干的就是这个,全程确定性规则,没有 LLM。

三个常见误解:

- **推不出常识**。RDFS 蕴含只认词表里白纸黑字的规则,「鸟会飞」这种世界知识推不了——它是查词典,不是开脑洞。
- **层级是单向的**。狗→动物推得上去;「是动物」推不回「是狗」。
- **蕴含≠已存储**。推出来的句子没存盘它也「成立」;什么时候物化成三元组,是工程决策。

## 三、附录 · 实操(卡片第 7 页)

### 3.1 交换备忘:媒体类型与场景选择

| 语法 | 媒体类型 | 扩展名 | 何时用 |
|---|---|---|---|
| Turtle | `text/turtle`(恒 UTF-8) | `.ttl` | 人写、人读、版本管理 |
| N-Triples | `application/n-triples` | `.nt` | 逐行流式处理、逐条导入 |
| N-Quads | `application/n-quads` | `.nq` | 多图导出、图级溯源打包 |
| TriG | `application/trig` | `.trig` | 数据集的人读形式 |
| RDF/XML | `application/rdf+xml` | `.rdf .owl` | 遗留系统、XML 生态对接 |
| JSON-LD | `application/ld+json` | `.jsonld` | Web API、前端消费 |

每种语法都有正式的格式识别 IRI(如 `http://www.w3.org/ns/formats/N-Triples`),内容协商时用它声明自己。语法家族的包含关系记牢:**N-Triples ⊂ Turtle ⊂ TriG**——解析器往大兼容,反向不成立。

### 3.2 IRI 卫生与 Skolem 化清单

发 IRI 之前消灭非规范形态:

- 大写 scheme / 主机名
- 多余的百分号编码、小写 HEX
- 显式 `:80` / 空路径
- `/./` 与 `/../` 未消解
- 非 NFC 字符、Punycode 主机

Skolem 化要点:把空白节点换成数据集内唯一的生成 IRI;约定用 `/.well-known/genid/` 路径或 `urn:uuid:`,表明「这不是真资源」;换完之后跨文档引用、去重、图合并都有据可依。

### 3.3 工具速览

| 工具 | 路线 |
|---|---|
| Apache Jena / riot | Java 全家桶:全语法解析、校验、规范形输出 |
| rdflib (Python) | Python 生态标配:解析、序列化、SPARQL 一条龙 |
| raptor / rapper | C 家族轻量解析器,命令行批处理利器 |
| JSON-LD processors | 各语言均有实现,展开/压缩/框架三操作 |

### 3.4 实操坑清单

1. bnode 标签**不是标识符**:换一份文档就换了含义;要跨文档引用一律 Skolem 化成 IRI。
2. IRI 比较禁止规范化:`…#A` 与 `…#a`、`%7E` 与 `~` 都是不同资源;发 IRI 前先自规范(见 3.2)。
3. 词项相等 ≠ 值相等:`"1"^^xsd:integer` 与 `"01"^^xsd:integer` 去重时是两条。
4. 语言标签统一小写:值层面大小写无意义,但词项相等逐字符比对——`"x"@EN` 与 `"x"@en` 是两条。
5. 图名不指称图:别把「图 IRI」当资源描述的主语,除非另外声明它指什么。
6. `rdf:li` 只活在 RDF/XML 里,解析后变 `rdf:_n`;Turtle/SPARQL 里写它无效。
7. 容器开放、列表封闭:允许别人补成员用 Bag/Seq,数据结构定死用 List。
8. rdf:HTML / rdf:XMLLiteral 非规范:跨库可能不识别,交换场景慎用。
9. N-Triples ⊂ Turtle ⊂ TriG:解析器往大兼容,反向不成立。
10. fragment 的语义跟着媒体类型走:同一 IRI 在 HTML 视图和 RDF 视图里指向的东西要约定一致。
