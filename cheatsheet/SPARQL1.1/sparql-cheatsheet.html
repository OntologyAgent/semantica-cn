01总览 · RDF 的查询语言 PART 1 · OVERVIEW

SPARQL:一条查询五段式,WHERE 里图模式组合出匹配,引擎按数据集求值,经协议返回结果;Update 让它读写对等。

主线:图模式是内功:一切查询都是基本图模式 + 算子的组合。
本卡结构 = 本图:概览 → 查询核心 → 修饰与函数 → 执行与更新 → 生态与实操。

03查询骨架 · 一条查询的五段式 PART 1 · QUERY ANATOMY
五种查询形态:SELECT 出变量表;CONSTRUCT 出图(模板重组);ASK 出真假;DESCRIBE 出关于某资源的子图(由实现自定——可移植性差的根源)。
# 骨架示例:谁在 2026 年发表过含 "kg" 的论文 PREFIX ex: <http://example.org/> SELECT DISTINCT ?author ?title WHERE { ?paper a ex:Paper ; ex:title ?title ; ex:author ?author . FILTER(CONTAINS(LCASE(?title), "kg")) ?paper ex:published ?date . FILTER(YEAR(?date) = 2026) } ORDER BY DESC(?date) LIMIT 20

04图模式算子 · 组合的基本功 PART 2 · GRAPH PATTERN ALGEBRA
算子写法语义要点
基础图模式三元组序列同组内共享变量,全部匹配
并{ P1 } UNION { P2 }两模式解集取并——各自独立求值
可选OPTIONAL { P }左外连接:匹配不上留空变量;配 BOUND(?v) 判空
过滤FILTER(expr)只作用于所在组;EXISTS / NOT EXISTS 内可引用组内变量
差MINUS { P }减去可兼容的解——见下一节,与 NOT EXISTS 有别
绑定BIND(expr AS ?v)表达式赋值;不能覆盖已有变量
内联值表VALUES ?x { a b }解集硬编码;可 JOIN 进模式
子查询{ SELECT … WHERE {…} }先内后外;内层先做完修饰再 join
# OPTIONAL + 聚合:有人没邮箱也要出现在报表里 SELECT ?person (COUNT(?mail) AS ?mails) WHERE { ?person a foaf:Person . OPTIONAL { ?person foaf:mbox ?mail } } GROUP BY ?person
05MINUS vs NOT EXISTS · 一字千金的差别 PART 2 · MINUS VS NOT EXISTS
# 谁没有邮箱 —— 两种写法 # ① MINUS:对「已有解」做集合减法 SELECT ?p WHERE { ?p a foaf:Person MINUS { ?p foaf:mbox ?m } } # ② NOT EXISTS:逐解判定,内层是过滤器 SELECT ?p WHERE { ?p a foaf:Person FILTER(NOT EXISTS { ?p foaf:mbox ?m }) }
差别在哪 MINUS 按共享变量相减:两模式没有共享变量时,MINUS 减不掉任何东西(全保留);NOT EXISTS 是逐解相关子查询,永远按内层模式判定。性能上 MINUS 常更优,语义上 NOT EXISTS 更直观——两边都要懂。

07聚合与分组 · 七个函数包打报表 PART 3 · AGGREGATES & GROUPING
聚合作用备注
COUNT(*) / COUNT(?v) / COUNT(DISTINCT ?v)计数* 数解,?v 数非空值
SUM / AVG / MIN / MAX求和均值极值数值型字面量
GROUP_CONCAT(?v ; separator=", ")串接顺序不保证——要排序先在子查询里 ORDER BY
SAMPLE(?v)任意取一个哪由实现定,别当确定性用
投影纪律 GROUP BY 之后,SELECT 里只能出现分组变量与聚合——「非聚合裸变量」直接报错,这是 SPARQL 对 SQL 用户的第一个下马威。

09数据集与命名图 · 一次查多张图 PART 3 · DATASETS & NAMED GRAPHS
# FROM 定默认图,FROM NAMED 挂命名图 SELECT ?who ?g FROM <http://example.org/default> FROM NAMED <http://example.org/graph:alice> FROM NAMED <http://example.org/graph:bob> WHERE { GRAPH ?g { ?s foaf:knows ?who } } # 不写 FROM:用端点默认配置;GRAPH ?g 遍历所有命名图 SELECT ?g ?s WHERE { GRAPH ?g { ?s ?p ?o } }

两组关键词 scope

  • FROM / FROM NAMED:组成查询数据集——不匹配的图被排除在考虑之外
  • GRAPH ?g { … }:在命名图内匹配;变量 ?g 绑定图名

与 RDF 1.1 数据集 差异

  • SPARQL 的图名只许 IRI,RDF 1.1 允许 bnode(引 PL.01 §07)——先 Skolem 化
  • 端点默认数据集由实现决定:查之前先看 Service Description
为什么要有命名图 溯源分账、多版本共存、权限隔离——都靠「哪条三元组属于哪张图」。SPARQL Update 与 Graph Store 协议同样按图操作。

13联邦查询 · SERVICE 与分布式 joins PART 5 · FEDERATED QUERY
# 把 Wikidata 的片段拉进本地模式 SELECT ?label ?country WHERE { :alice foaf:based_near ?city . SERVICE <https://query.wikidata.org/sparql> { ?city rdfs:label ?label . ?city wdt:P17 ?country . FILTER(LANG(?label) = "zh") } }
联邦的代价 SERVICE 是黑盒:过滤下推靠各端点自觉,慢查询是常态。把可下推的 FILTER 写进 SERVICE 块内部、必要时用 VALUES 预绑关键变量,能省一个数量级。

正在路上(检索于 2026-10) SPARQL 1.2 由同一工作组推进(十二份文档,引 PL.06 §02):核心看点是与 RDF 1.2 对齐——三元词项可进查询模式、方向性语言标签的函数支持、Canonical SPARQL(规范化查询形)。本文的 1.1 内容全部是其子集。
15实操坑清单 PART 5 · PITFALLS
  1. OPTIONAL 里套 FILTER:过滤留在 OPTIONAL 组内部才按预期工作,挪到外层语义就变。
  2. MINUS 无共享变量 = 白减;该用 NOT EXISTS 的场景别图省事。
  3. GROUP BY 后 SELECT 只许分组变量与聚合——裸变量直接报错。
  4. GROUP_CONCAT 顺序不保证:要有序,先子查询排序再聚合。
  5. OFFSET 翻页必须配 ORDER BY,否则页与页会重叠漏数据。
  6. p* 恒含零步(自己到自己),要「严格后代」用 p+。
  7. DESCRIBE 的子图范围由实现自定——跨端点结果不可比,生产查询写 SELECT。
  8. 字面量比较认类型:"5" ≠ 5;数值过滤前先 FILTER(datatype) 或统一类型。
  9. 语言标注串比较用 langMatches(lang(?v),"zh"),直接 = "zh" 会漏掉 zh-CN。
  10. Update 默认无事务保证(端点自行决定):大批改动拆批 + 校验,别指望回滚。
  11. SERVICE 里写死大模式:下推过滤、VALUES 预绑,否则联邦查询慢出天际。
  12. 空 WHERE / 空模式在 update 里是合法边界(全图操作),手滑写空的 DELETE WHERE = 清库。
