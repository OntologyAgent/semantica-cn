# 本体建模流水线落地：九个阶段的代码与契约

> 本篇是「本体建模最佳实践」文档集第二篇。前置阅读：[第一篇 总纲](本体建模最佳实践.md)（29 句话与四铁律）；各阶段「注入版」的完整提示词模板（A–I）统一收在[第三篇](本体建模-03-提示词与双模型协同.md)，本篇只给调用方式。
>
> 全部代码对齐 **Semantica 0.6.7**（以 [StockInsight](../../projects/StockInsight/GUIDE.md) 真实财报流水线的已验证调用为基准；官方文档标注 0.5.0，个别 API 与实装有差异，裁定规则见[第四篇](本体建模-04-能力边界与替代方案.md)）。环境前置：`semantica doctor` 验证安装；LLM 抽取段需要 API key（配置见第三篇），无 key 的段落用 `method="pattern"` 也能走通。

## 开篇：变量流总图

九个阶段不是九个孤岛，而是一条**变量流**：每个阶段消费上一阶段的产物变量，产出下一阶段的输入变量。这张图是本篇的骨架，先记住变量名，后面每一节都在传递它们。

```
raw 文档（StockInsight: stocks/00100/raw/ 公告 PDF + 新闻 MD）
  │ ① 多源萃取：ingest → parse → split
  ▼
chunks: List[Chunk]                     # text / start_index / end_index / metadata / id
  │ ② 语义标准化：NER + 关系 + 事件抽取（LLM 或 pattern）
  ▼
entities / relationships / events       # 统一为 List[dict]（对象转 dict 的约定见 3.2）
  │ ③ 术语归一：规范化 + 指代消解 + 别名合并
  ▼
normalized_entities + glossary          # 规范名实体集 + 别名词表（29 句话第 3 类的产物）
  │ ④ 冲突去重：detect → resolve → dedup（顺序铁律：冲突先于合并）
  ▼
clean_entities / clean_relationships    # MergeOperation(合并产物) + 孤立实体 拼成的完整集
  │ ⑤ 本体建模：from_data 数据驱动 / 注入版 to_owl
  ▼
ontology: dict（classes/properties）    # + Turtle（to_owl 生成）+ SHACL shapes
  │ ⑥ 规则推理与审计：Reasoner / Datalog + 双模型审计
  ▼
signals: List[InferenceResult] + 审计报告
  │ ⑦ 建图与校验：GraphBuilder → GraphValidator → SHACL validate_graph
  ▼
graph: dict（校验通过）                # entities/relationships 两键
  │ ⑧ 场景测试：黄金用例 + CQ 验收 + 推理断言
  ▼
graph + 测试报告（失败按三分类退回 ⑤⑥⑦）
  │ ⑨ 资产入库：溯源四元组 + 导出 + 决策记录 + 版本快照
  ▼
资产（Turtle/Parquet + PROV 记录 + 决策对象）→ 下游（Explorer / FalkorDB / Agent）
```

贯穿案例约定：**StockInsight 项目**（港股 00100 MiniMax 投资知识图谱），raw 数据 98 个文件（44 份公告 PDF、3 份 HTM、49 份新闻/研究 MD、2 份索引 JSON），五数据域（公告/新闻/行情/基本面/宏观）中公告与新闻域已验证跑通。每阶段末尾有「换领域时怎么适配」——这套流水线不绑定金融。

## 3.1 多源萃取

**目标**：取回原料、解析成文本、切成带来源的分块。不落库。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | raw 文档路径（文件/目录/URL）。StockInsight：`stocks/00100/raw/` 下 `2026082600681_c.pdf`（公告）、`news_2026-08-26_minimax-h1.md`（新闻） |
| 输出 | `chunks: List[Chunk]`，字段 `text / start_index / end_index / metadata / id`；每块 `metadata["source"]` 记原始路径。判据：全覆盖无丢块、无空块，分块落在语义边界 |
| 前置依赖 | 数据域清单已定（StockInsight 的 PLAN.md）；PDF 可读（`DocumentParser` 内置 pdfplumber） |
| 后续流向 | 全部交给 3.2 做抽取；`metadata.source` 一路带到 3.9 的溯源 |

```python
from semantica.ingest import FileIngestor
from semantica.parse import DocumentParser
from semantica.split import TextSplitter

# ① 摄取：拿回带 path/text 的源对象（StockInsight 已验证写法）
src = FileIngestor().ingest_file("projects/StockInsight/stocks/00100/raw/2026082600681_c.pdf")

# ② 解析：PDF → dict（含正文与页信息；0.6.7 正文键兼容 text/full_text）
parsed = DocumentParser().parse(src.path)
text = parsed.get("full_text") or parsed.get("text")

# ③ 分块：relation_aware 保证 (主语,谓语,宾语) 不被切断（KG 管道官方推荐）
splitter = TextSplitter(method="relation_aware", chunk_size=1200, chunk_overlap=100)
chunks = splitter.split(text)
for c in chunks:
    c.metadata["source"] = src.path        # 溯源从第一站开始，不可断
```

**校验点**：每块有唯一来源；无空块、残块；巨型文档先截断抽样（StockInsight 实践：>20000 字截前 2 万、1200 字分块、每块最多重试 3 次）。

**实践模式**（[cookbook 11 分块](../../cookbook/introduction/11_Chunking_and_Splitting.ipynb)）：KG 场景优先 `relation_aware`（保三元组完整），其次是 `entity_aware`（不切断实体名）；固定字数切块是最下策。

**换领域怎么适配**：数据域清单换成你的领域（制造：工单+设备手册+点检记录；医疗：病历+指南+药品说明书）。分块策略不变；表格多的原料（财报/检验单）解析后检查 `parsed["tables"]` 是否丢失数值。

## 3.2 语义标准化（29 句话当抽取目标）

**目标**：把 chunks 抽成类型化的实体/关系/事件。抽取目标以 29 句话的七类语义为纲（第①②⑤类在这里落地），不让 LLM 自由发挥。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 3.1 的 `chunks`；LLM 配置（provider/base_url/model/api_key，见第三篇） |
| 输出 | `entities / relationships / events: List[dict]`。统一约定：**对象一律转 dict**——Entity → `{"id","text","type","confidence","start","end"}`；Relationship → `{"source","target","type","confidence","metadata"}`；Event → 九字段（见代码注释）。判据：置信度过滤后非空、三要素齐全、关系方向不反、事件单独成列 |
| 前置依赖 | 3.1 完成；LLM 端点可用（或用 pattern 法离线跑） |
| 后续流向 | entities/relationships → 3.3 术语归一；events → 直接随 3.7 入图（事件不参与术语归一） |

**默认版**（库内置提示词，StockInsight 已验证签名）：

```python
import os
from semantica.semantic_extract import NERExtractor, RelationExtractor, EventDetector

# 0.6.7 实测要点：provider 必须是 "openai" 字符串 + OpenAI 兼容端点；
# 智谱唯一可用端点是 https://open.bigmodel.cn/api/coding/paas/v4
kw = dict(provider="openai", model="glm-5.3-flash",
          base_url="https://open.bigmodel.cn/api/coding/paas/v4",
          api_key=os.environ["ZHIPU_API_KEY"])

ner  = NERExtractor(method="llm", **kw)
rel  = RelationExtractor(method="llm", **kw)

entities = ner.extract(chunk.text)          # List[Entity]，字段 text/label/confidence/start_char/end_char（0.6.7 实装口径）
relationships = rel.extract(chunk.text, entities=entities)  # 关系抽取必须显式传入 NER 结果
events = EventDetector(method="llm", **kw).detect_events(chunk.text)
# Event: text/event_type/start_char/end_char/participants/location/time/confidence/metadata
```

离线/零依赖替代：`NERExtractor(method="pattern")`（无需 key，质量有限，适合最小链路验证）；回退链 `method=["llm", "pattern"]` 保证非空（[semantic_extract 参考](../reference/semantic_extract.md)）。

**对象转 dict**（下游 conflicts/dedup/GraphBuilder 全部吃 `List[Dict]`，这步转换不做，3.4 就断档）：

```python
entities_d = [{"id": f"e{i}", "text": e.text, "type": e.label,   # 对象属性是 label，dict 约定键用 type
               "confidence": e.confidence, "metadata": {"source": chunk.metadata["source"]}}
              for i, e in enumerate(entities, 1)]
```

**注入版**：用自己的提示词模板控制抽取目标（模板 A——实体/三元组双 schema + 原文子串约束），经 `create_provider(...).generate_typed(prompt, schema=EntitiesResponse)` 走 Pydantic 硬校验。完整模板与调用代码见第三篇。

**校验点**：置信度阈值前置过滤（生产建议实体 0.7–0.8、关系 0.6–0.7，[cookbook 05](../../cookbook/introduction/05_Entity_Extraction.ipynb)）；同实体跨块同名（交给 3.3 归一）；事件不塞进三元组。

**换领域怎么适配**：实体类型表（type 词表）换成领域本体类型——投资域是 Company/Person/Product/Concept，制造域是 Device/Process/Fault/Material。类型词表就是 3.5 数据驱动建本体的输入，抽取和建模共用一张表。

## 3.3 术语归一

**目标**：同物异名归一到规范名，指代消解，沉淀别名词表。这是 29 句话第 3 类（业务术语）的落地。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 3.2 的 `entities_d`（List[dict]）+ 原文 chunks（指代消解需要上下文） |
| 输出 | `normalized_entities`（每条有规范名与**规范 ID**；同一实体的多来源记录此时**共享同一 ID 但尚未合并**——合并是 3.4 的事，先合并会把多来源差异藏掉）+ `glossary: dict`（`{"规范名": ["别名", ...]}`，追加不覆盖）。判据：同义异形已归到同一 ID、每实体有类型、词表无重复主词 |
| 前置依赖 | 3.2 完成；领域术语表初版（人工先建种子别名，LLM 抽取的别名经人工确认后并入） |
| 后续流向 | `normalized_entities` → 3.4 冲突去重（按 ID 分组检测多来源矛盾）；`glossary` → 3.5 注入版建模的输入 + 长期资产 |

```python
from semantica.normalize import TextNormalizer, EntityNormalizer
from semantica.semantic_extract import CoreferenceResolver
from semantica.deduplication import detect_duplicates, merge_entities

# ① 文本规范化先行（NER 前勿 lowercase；这里是对抽取结果的清洗）
tn = TextNormalizer()
for e in entities_d:
    e["text"] = tn.normalize_text(e["text"], unicode_form="NFC")

# ② 指代消解：resolve(text, entities=) 返回 CoreferenceChain 列表
resolver = CoreferenceResolver()
chains = resolver.resolve(chunk.text, entities=entities_d)
# 每条 chain 指向同一现实实体：把 chain 成员的名字统一到首个规范名

# ③ 别名归一：EntityNormalizer 需要 alias_map（无内置公司后缀展开，必须显式给）
alias_map = {"MiniMax": "MiniMax Group Inc.", "稀宇科技": "MiniMax Group Inc.",
             "MiniMax-W": "MiniMax Group Inc."}          # 种子 + 人工确认的 LLM 产出
en = EntityNormalizer(alias_map=alias_map)
for e in entities_d:
    e["text"] = en.normalize_entity(e["text"], entity_type=e["type"])
    e["id"] = canonical_id(e["text"])                    # 同实体（含多来源）统一到同一 ID

# ④ 合并预览（本阶段不合并！）：先看有多少重复候选，合并动作留给 3.4（冲突消解之后）
dup_pairs = detect_duplicates(entities_d)                # List[DuplicateCandidate]，只看不动
```

> 顺序为什么这么排：冲突检测按**实体 ID 分组**找多来源矛盾（3.4），如果在这里就合并，多来源的差异会被「合并策略」悄悄裁决掉，冲突永远检不出来——这正是官方「Detect before you merge」的落点。

**校验点**：合并后无「同规范名多 ID」残留；`glossary` 每个规范名只出现一次；**图中无裸指代实体**——实体名落在指代词表（本公司/本集团/发行人/该公司…，随数据源自称习惯扩充）即不准入。这类自称的先行词在文档元信息（如披露易公告的发行人）而非正文，通用共指消解（`CoreferenceResolver`）链不到它们，必须靠**领域自称词表**在归一阶段显式消解——StockInsight 实测 91 条边挂在「本公司/本集团」假枢纽上漏网，直到人工审图才发现。抽取侧同步约束：3.2 的提示词应写明「文中的发行人自称一律替换为主体全名再抽取」，两层一起堵。

**实践模式**（[cookbook 07](../../cookbook/introduction/07_Building_Knowledge_Graphs.ipynb)）：

- **span 映射建边**：关系的端点按实体的 `(start, end)` 字符偏移查映射表得到，查不到就跳过并记日志——绝不按列表位置猜端点。
- **消解后重映射**：用合并产物的 `merged_from`（若有）构建 `旧ID → 规范ID` 映射，把所有关系端点改指规范实体。

**换领域怎么适配**：`alias_map` 的种子从领域术语表来——投资域是公司简称/代码/曾用名；制造域是设备位号/俗称/型号。术语表越准，这阶段的自动化程度越高；冷启动靠人工 30–50 条种子。跨字符集数据源（如港台繁体公告 + 大陆简体新闻）还要在 id 归一前做**繁简转换**（OpenCC t2s），否则同一概念会以两副面孔各建一实体——StockInsight 实测 88 组/182 个实体因此分裂。

## 3.4 冲突去重

**目标**：先标记冲突再消解，最后去重，禁止静默覆盖。官方铁律：**Detect before you merge, not after**——图里合并后原始来源归属会丢（[conflicts 参考](../reference/conflicts.md)）。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 3.3 的 `normalized_entities`（**同 ID 多来源记录并存**：公告说 A、媒体说 B，都还在——ID 相同是冲突检测的分组键）+ 可选 `relationships` |
| 输出 | 冲突报告（`List[Conflict]`）→ 消解决策（method 留痕）→ `clean_entities / clean_relationships`（MergeOperation 合并产物 + 孤立实体拼成完整集）。判据：冲突清零或全部挂人工审查；产物无静默覆盖 |
| 前置依赖 | 3.3 完成；**来源可信度已注册**（不注册则 credibility 加权退化为投票） |
| 后续流向 | 干净集 → 3.5 建模与 3.7 建图；冲突裁决记录 → 3.9 决策留痕 |

```python
from semantica.conflicts import (SourceTracker, detect_conflicts,
                                 resolve_conflicts, ConflictAnalyzer)

# ① 先注册来源可信度（默认 0.50；不注册，credibility_weighted 等同 voting）
tracker = SourceTracker()
tracker.register_source("hkexnews", source_type="official", credibility_score=0.95)  # 披露易公告
tracker.register_source("media", source_type="media", credibility_score=0.70)        # 新闻

# ② 检测：便捷函数签名是 detect_conflicts(entities, method=, property_name=)
#    按「同一 ID 多来源记录」分组，找出值/类型矛盾
#    method 合法值：value/type/relationship/temporal/logical/entity
#    注意：TEMPORAL/LOGICAL 在 0.6.7 的 ConflictDetector 上未实现，勿选（见第四篇）
conflicts = detect_conflicts(normalized_entities, method="value", property_name="revenue")
#    示例输入长这样（同 id、不同 source、不同值）：
#    {"id": "minimax", "revenue": "116.6M", "source": "hkexnews"}
#    {"id": "minimax", "revenue": "110.0M", "source": "media"}
#    → 1 条 VALUE_CONFLICT，severity=critical
conflicts += detect_conflicts(normalized_entities, method="type")   # 类型冲突也查一遍

# ③ 消解：method 可选 voting/credibility_weighted/most_recent/highest_confidence/expert_review
#    关键字段冲突（财务数据）走专家；一般字段走可信度加权
resolved = resolve_conflicts(conflicts, method="credibility_weighted")
#    每条结果带 resolved 标志与所选值，据此更新实体记录（或挂人工审查）

# ④ 消解之后才合并：merge_entities(entities, method=...) → List[MergeOperation]
from semantica.deduplication import merge_entities
ops = merge_entities(normalized_entities, method="keep_most_complete")
merged_ids = {src_e["id"] for op in ops for src_e in op.source_entities}
clean_entities = [op.merged_entity for op in ops] + \
                 [e for e in normalized_entities if e["id"] not in merged_ids]
#    完整集 = 合并产物 + 未参与合并的孤立实体（漏掉后者是常见 bug）

# ⑤ 分析系统性冲突源（哪个来源总是打架），反哺可信度分数
from semantica.conflicts import ConflictAnalyzer
report = ConflictAnalyzer().analyze_conflicts(conflicts)   # patterns/by_severity/by_source
```

**校验点**：冲突全部被标记且留裁决依据；顺序铁律 `conflicts → dedup → kg` 不可颠倒；人工审查的冲突生成调查指南（`InvestigationGuideGenerator().generate_guide(conflict)`，[cookbook 17](../../cookbook/introduction/17_Conflict_Detection_and_Resolution.ipynb)）。

**换领域怎么适配**：可信度排序换领域事实——投资域「公告 > 新闻 > 宏观推断」；医疗域「指南 > 病历 > 患者自述」。`property_name` 优先挑领域里最要命的数值字段（投资的收入、医疗的剂量）。

## 3.5 本体建模

**目标**：建类层次、属性边界、术语与规则的骨架。两条路线：**数据驱动**（从抽取结果推导，确定性）与**注入版**（29 句话描述 → LLM 产出本体 dict）。有图之后优先数据驱动——确定性、可复现、不耗 token（[ontology 指南](../guides/ontology.md)）。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 数据驱动：3.4 的 `clean_entities / clean_relationships`。注入版：篇1 的 29 句话实例化描述 + `glossary` 术语表（经四铁律审核通过） |
| 输出 | `ontology: dict`（`classes: [{name,label,comment,parent}]`、`properties: [{name,type:object\|data,domain,range}]`）+ Turtle（`to_owl` 生成，不让 LLM 写）+ SHACL shapes。判据：`validate_ontology` 通过、能力题验收 answerable |
| 前置依赖 | 3.4 干净集；29 句话产出（注入版）；命名空间 `base_uri` 已定 |
| 后续流向 | ontology → 3.6 规则（类/属性是规则的谓词来源）、3.7 SHACL 验证、3.9 导出与版本 |

**默认版·数据驱动**（StockInsight 已验证）：

```python
from semantica.ontology import OntologyEngine, validate_ontology

engine = OntologyEngine(base_uri="https://investment.example/ontology/")
ontology = engine.from_data({"entities": clean_entities,
                             "relationships": clean_relationships})
# from_data 只吃 entities/relationships——从数据推导类与属性；
# 它不接受现成的 classes/properties 定义（注入版的差异见下）

report = validate_ontology(ontology)          # → {valid, warnings, errors}
turtle = engine.to_owl(ontology, format="turtle")   # Turtle 由库确定性生成
shacl  = engine.to_shacl(ontology, format="turtle") # required 属性装载时强制
```

需要细控时用三件套（[cookbook 14](../../cookbook/introduction/14_Ontology.ipynb)）：

```python
from semantica.ontology import ClassInferrer, PropertyGenerator, OntologyOptimizer

classes = ClassInferrer(min_occurrences=2).infer_classes(clean_entities, build_hierarchy=True)
properties = PropertyGenerator().infer_properties(
    entities=clean_entities, relationships=clean_relationships, classes=classes)
ontology = OntologyOptimizer().optimize_ontology(ontology, remove_redundancy=True)
```

**注入版**（29 句话 → 本体 dict）：LLM 按模板 D 产出与 `from_data` 同构的本体 dict，再交库生成 Turtle。**关键差异**：注入版的 dict 不走 `from_data`（它只认 entities/relationships），而是**规范 `uri` 键后直接喂 `to_owl`**——`to_owl` 读的是 `ontology.get("uri")`：

```python
# data 是模板 D 的 LLM 产出（classes/properties 已齐）
data["uri"] = data.pop("base_uri")           # 关键：to_owl 认 uri 键
turtle = engine.to_owl(data, format="turtle")
```

**能力题验收**（29 句话的每句实例化成一条能力题）：

```python
from semantica.ontology import CompetencyQuestionsManager

mgr = CompetencyQuestionsManager()
mgr.add_question("MiniMax 2026H1 开放平台收入占收入的比例是多少？", category="业务对象", priority=1)
mgr.add_question("什么条件下触发 HOLD_AND_MONITOR 策略？", category="业务规则", priority=1)
result = mgr.validate_ontology(ontology)
# 返回 dict：total_questions / answerable / unanswerable / by_category（int 计数）
# 逐题状态在 mgr.questions[i].answerable；判定是类名/属性名的关键词启发式，
# 「answerable」不代表推理链已通——推理验证在 3.8 做
```

**校验点**：类无环、无孤立类；属性 domain/range 一致；29 句话每句要么落进本体、要么挂「不适用」说明；等价/互斥对齐术语表（`equivalentClass`/`disjointWith`）。

**实践模式**（[cookbook advanced/13 手工本体](../../cookbook/advanced/13_Manual_Ontology_Snowflake_Mapping.ipynb)，官方唯一「最佳实践架构」教程）：**本体即代码**——本体 dict 手写显式（类/属性/domain/range 全显式），与代码一起版本化，不从 schema 推断本体，避免每次数据迁移静默改变语义模型；属性与关系类型带完整 URI，防止存储落默认命名空间导致 SPARQL 前缀查空。

**换领域怎么适配**：`base_uri` 换领域命名空间；29 句话的实例化是领域术语表 → 领域类目的转写（投资域「公司/持仓/财务指标/事件/策略」，制造域「设备/工艺/故障/物料/工单」）。三条骨架不变：先数据驱动出骨架，人工按 29 句话补全，CQ 验收收口。

## 3.6 规则推理与审计

**目标**：把 29 句话第 4 类（业务触发规则）翻译成可执行规则，前向推隐含信号、后向答能力题；再让独立审计器把关（双模型协同）。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 规则清单（从 29 句话 4.1 实例化来，如「毛利率连续下滑且亏损扩大 → HOLD_AND_MONITOR」）；事实集（3.4 干净集转成 `"Predicate(args)"` 字符串）；待审本体（3.5 的 ontology/Turtle） |
| 输出 | `signals: List[InferenceResult]` + 审计报告（verdict/issues 列表）。判据：无闭环冲突、无自相矛盾、无悬空变量；审计 verdict=pass |
| 前置依赖 | 3.5 完成（规则的谓词必须来自本体的类/属性）；审计器 LLM 配置（第三篇模板 F） |
| 后续流向 | signals → 3.8 场景测试与 3.9 决策依据；审计不过 → **退回 3.5**（修本体）或改规则清单重跑 |

```python
from semantica.reasoning import Reasoner, DatalogReasoner

r = Reasoner()
# 规则格式铁律：IF <条件> AND <条件> THEN <结论>（单行字符串）
# 坑：不匹配此格式的规则会被静默解析成「永不触发的空条件规则」，不报错（见第四篇）
r.add_rule("IF gross_margin_declining(?c) AND loss_widening(?c) THEN hold_and_monitor(?c)")

r.add_fact("gross_margin_declining(minimax)")
r.add_fact("loss_widening(minimax)")

signals = r.forward_chain()                       # → 推出 hold_and_monitor(minimax)
answer  = r.backward_chain("hold_and_monitor(minimax)")   # 回答能力题，None=推不出
```

递归/传递闭包用 Datalog（变量必须大写、无 `?` 前缀；常量小写开头）：

```python
dr = DatalogReasoner()
dr.add_rule("indirect_subsidiary(X, Y) :- subsidiary_of(X, Y).")
dr.add_rule("indirect_subsidiary(X, Z) :- subsidiary_of(X, Y), indirect_subsidiary(Y, Z).")
for rel in clean_relationships:                   # KG 关系 dict 可直接入
    dr.add_fact(rel)                              # {source,target,type} → 谓词(端点)
dr.derive_all()                                   # semi-naive 不动点，保证终止
rows = dr.query("indirect_subsidiary(X, Y)")
```

**审计**（双模型协同，第二篇不展开模板）：生成者 LLM（A）产出本体，审计者 LLM（B）按三维度出《本体语义缺陷报告》——语法规范/逻辑一致/业务贴合，A 对质疑辩护或修订，分歧推送人工仲裁。完整 Prompt 与三步闭环见第三篇。

**校验点**：正反例都能解释（推得出的推得出、推不出的推不出）；规则条件变量全部被本体类/属性约束；审计 issue 清零或降级为 info。

**换领域怎么适配**：规则模板跟着决策场景走——投资域「财务指标组合 → 持仓动作」；制造域「传感器组合 → 维护工单」。写法完全一致：条件原子对应本体属性，结论原子对应业务动作。

## 3.7 建图与校验

**目标**：把干净集与本体的成果合并成图，三道校验（结构、类型词汇、SHACL），再可视化给专家审。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 3.4 的 `clean_entities / clean_relationships` 打包成 `{"entities": [...], "relationships": [...]}`；3.5 的 `ontology`（SHACL 用）；3.6 审计通过 |
| 输出 | `graph: dict`（`graph["entities"]` / `graph["relationships"]` 可计数）。判据：`GraphValidator().validate(graph).is_valid` 为 True；SHACL `validate_graph(...).conforms` 为 True |
| 前置依赖 | 3.4/3.5/3.6 全过；如需持久化，图库连接就绪（可选） |
| 后续流向 | graph → 3.8 场景测试 → 3.9 资产入库；可视化 HTML 给专家评审（F 模板评审引导见第三篇） |

```python
from semantica.kg import GraphBuilder, GraphValidator
from semantica.export import RDFExporter

# ① 建图：build 接受一个 dict（不支持 entities=/relationships= 关键字），本身返回 dict
#    merge_entities 只对「未经 3.4 去重的原始输入」开；已按规范 id 折叠的干净集
#    要传 False（默认值）——否则二次模糊合并会把不同实体并掉、顶掉规范名（见第四篇）
builder = GraphBuilder(merge_entities=False)
graph = builder.build({"entities": clean_entities, "relationships": clean_relationships})

# ② 结构校验 + 悬挂边自动修复（cookbook advanced/02 的门禁模式）
validator = GraphValidator()
v = validator.validate(graph)
if not v.is_valid:
    for issue in v.issues:
        if issue.code == "DANGLING_EDGE":       # 悬挂边：过滤坏关系后必须复检
            clean_relationships = [r for r in clean_relationships
                                   if r.get("target") != issue.details.get("target_id")]
    graph = builder.build({"entities": clean_entities, "relationships": clean_relationships})
    assert validator.validate(graph).is_valid   # 修复必须复检确认

# ③ 类型词汇校验：schema 是「本体进 KG 构建」的显式通道（本体的类型约束在图的入口生效）
v2 = GraphValidator().validate(graph, schema={
    "entity_types": ["Company", "FinancialMetric", "Product", "Executive"],
    "relationship_types": ["reports", "has_metric", "released", "subsidiary_of"]})

# ④ SHACL 验证：注意 data_graph 必须是 RDF 字符串或 rdflib.Graph（dict 不行，先导出）
#    依赖前置：validate_graph 需要可选依赖 pyshacl（uv pip install "semantica[shacl]"），缺了抛 ImportError
rdf_text = RDFExporter().export_to_rdf(graph, format="turtle")
report = engine.validate_graph(rdf_text, ontology=ontology)   # shapes 由 ontology 自动生成
print(report.conforms, len(report.violations))
```

**可视化**：`KGVisualizer().visualize_network(graph, output="html", file_path="graph.html")` 产出交互页面（确定性渲染）；把图交给业务专家按「全局拓扑 → 局部语义 → 规则回溯」三步审（篇1 四铁律的复核环节），评审引导与采集反馈的模板见第三篇。

**校验点**：三道校验全过；可视化页面专家可判读（类/关系用业务语言标注）；图分析前记得转换——`GraphBuilder.build()` 返回 dict，`PathFinder`/`GraphAnalyzer` 要 networkx 图（StockInsight 踩坑实录）。

**换领域怎么适配**：schema 的类型词汇表直接用 3.5 的本体类目；SHACL 验证零改动。可视化标注语言用领域话术（专家看「持仓组合」不看「Strategy 节点」）。

## 3.8 场景测试

**目标**：从「形式正确」到「业务可用」——黄金用例 + AI 测试矩阵 + 结果回溯，这是交付前最后的质量防线（书稿 6.2.4）。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 3.7 的 `graph` + 3.5 的 `ontology` + 专家黄金用例（核心流程、关键决策点、典型异常）+ 3.6 的 `signals` |
| 输出 | 测试报告（每用例 通过/失败/错误 + 归因）。判据：核心用例全过；失败全部归因到三类之一并触发回退 |
| 前置依赖 | 3.7 校验通过；专家已定义黄金用例（预期结果必须明确到可断言） |
| 后续流向 | 全过 → 3.9 入库；失败 → **模型缺陷退 3.5、用例错误修用例、规则冲突退 3.6**（回退路径显式写进报告） |

```python
# 黄金用例（专家定义）：场景 + 核心问题 + 预期结果
GOLDEN = [
    ("MiniMax 2026H1 亏损收窄但收入大涨，策略是什么？",
     "hold_and_monitor(minimax)",                # 预期：可推出的结论
     "not hold_and_monitor(minimax)"),           # 预期：不应出现的结论（反例）
]

for question, expect_yes, expect_no in GOLDEN:
    assert r.backward_chain(expect_yes) is not None, f"推不出应推出的结论：{question}"
    assert r.backward_chain(expect_no) is None,     f"推出了不该推出的结论：{question}"

# CQ 复核（能力题逐题状态；总数口径见 3.5）
result = mgr.validate_ontology(ontology)
assert result["answerable"] >= result["total_questions"] - 1   # 允许 1 题挂起并说明
```

**AI 测试矩阵**：让 LLM 基于黄金用例扩边缘/异常/等价变异用例（模板 G，第三篇）——边界值（毛利率恰好持平）、组合冲突（两条规则同时命中）、反直觉（不该发生的当没发生）。测试集入库，作为后续演进的回归资产。

**校验点**：每用例有唯一可判定的预期；正反例同立；失败回退路径已在报告中标注（缺前置条件的边界用例是重点）。

**换领域怎么适配**：黄金用例就是领域的「老师傅三问」——投资域问「这种情况拿不拿」；制造域问「这个报警要不要停机」。预期结果必须写成可断言的谓词，不接受「合理即可」。

## 3.9 资产入库

**目标**：带来源与决策入库，版本化、可导出、可回滚。到这里，知识从原料变成资产。

**四要素契约**

| 要素 | 约定 |
|---|---|
| 输入 | 3.8 通过的 `graph`；溯源四元组（source/位置/原句/置信度，来自 3.1 起累积的 `metadata`）；决策描述（谁、依据、结论、置信度） |
| 输出 | PROV 溯源记录（SQLite 持久化）+ 导出文件（Turtle/Parquet/JSON）+ 决策对象（decision_id）+ 版本快照。判据：任一实体可 `get_lineage` 回原始文档；导出文件可被 Explorer/外部工具加载 |
| 前置依赖 | 3.8 全过；`storage_path` 已定（默认内存不跨进程）；导出目录可写 |
| 后续流向 | 下游消费：Knowledge Explorer 面板、图数据库（FalkorDB `graph=stock_00100`）、Agent 上下文（`AgentContext` + `find_precedents`） |

```python
from semantica.provenance import ProvenanceManager
from semantica.context import ContextGraph
from semantica.export import RDFExporter, ParquetExporter

# ① 审计级溯源：证据四元组（cookbook 22 模式），默认内存存储，跨进程必须给 storage_path
prov = ProvenanceManager(storage_path="projects/StockInsight/stocks/00100/provenance.db")
prov.track_entity("minimax", source="stocks/00100/raw/2026082600681_c.pdf",
                  source_location="第 8 页 中期业绩公告",
                  source_quote="截至2026年6月30日止六个月收入约为116.6百万美元",
                  confidence=0.95, entity_type="Company")
lineage = prov.get_lineage("minimax")     # source_documents / first_seen / lineage_chain
# 事实被更正时走 invalidate（留痕不删除）：prov.invalidate(entity_id, agent_id, reason)

# ② 导出：RDF（含溯源）+ Parquet（供 pandas 分析）
RDFExporter(include_provenance=True).export(graph, "final_graph.ttl", format="turtle")
ParquetExporter(compression="snappy").export_knowledge_graph(graph, "final_graph")
#   → final_graph-entities.parquet + final_graph-relationships.parquet
# CLI 等价：semantica export --format turtle --output final_graph.ttl

# ③ 决策即一等对象（回路的起点）
cg = ContextGraph()
decision_id = cg.record_decision(category="strategy", scenario="MiniMax 2026H1 中期业绩",
    reasoning="收入 +283% 且亏损收窄 11%，开放平台占 63%，成长与风险并存",
    outcome="HOLD_AND_MONITOR", confidence=0.72, decision_maker="investor-luo")

# ④ 版本快照（演进可回滚、可对比）。坑：author 必须是邮箱格式（ChangeLogEntry 校验）
from semantica.kg import TemporalVersionManager

                   description="MiniMax 2026H1 五域首版")
```

**校验点**：资产可回溯来源（抽查 `get_lineage`）；决策有决策人/时间/依据；版本可回滚（`vm.compare_versions("v1.0-h1", ...)`）；导入导出一致（Turtle 重新加载计数一致）。

**换领域怎么适配**：溯源的 `source_quote` 引领域原文（公告句/病历段/工单备注）；决策的 category/outcome 换领域动作词表。机制零改动。

## 附录：最小可跑链路

下面这条链路**不含 LLM 调用**（pattern 抽取零依赖零 key），在 `.venv`（Python 3.11 + semantica 0.6.7）实测可跑通，用于环境自检与新接手者跑通第一圈：

```python
"""最小可跑链路：摄取 → 解析 → 抽取(pattern) → 建图 → 校验 → 推理 → 断言"""
from semantica.ingest import FileIngestor
from semantica.parse import DocumentParser
from semantica.semantic_extract import NERExtractor
from semantica.kg import GraphBuilder, GraphValidator
from semantica.reasoning import Reasoner

# ① 摄取 + 解析（任意 txt 文本文件）
src = FileIngestor().ingest_file("data/sample.txt")
parsed = DocumentParser().parse(src.path)
text = parsed.get("full_text") or parsed.get("text")

# ② pattern 抽取（零依赖；生产换 method="llm"）
ents = NERExtractor(method="pattern").extract(text)
entities = [{"id": f"e{i}", "name": e.text, "type": e.label,
             "properties": {}, "confidence": e.confidence}
            for i, e in enumerate(ents, 1)]
relationships = []                       # pattern 法不产关系；LLM 版见 3.2

# ③ 建图 + 结构校验
graph = GraphBuilder(merge_entities=True).build(
    {"entities": entities, "relationships": relationships})
v = GraphValidator().validate(graph)
assert v.is_valid, [i.code for i in v.issues]

# ④ 推理断言（正例推得出、反例推不出）
r = Reasoner()
r.add_rule("IF high_growth(?c) AND loss_narrowing(?c) THEN hold_and_monitor(?c)")
r.add_fact("high_growth(minimax)")
r.add_fact("loss_narrowing(minimax)")
r.forward_chain()
assert r.backward_chain("hold_and_monitor(minimax)") is not None
assert r.backward_chain("hold_and_monitor(unknown)") is None
print(f"最小链路通过：{len(graph['entities'])} 实体，推理断言全过")
```

依赖 LLM/外部后端的段落（3.2 llm 抽取、3.5 from_text、3.6 审计），先跑 `semantica doctor`。
