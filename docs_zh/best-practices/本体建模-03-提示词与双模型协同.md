# 提示词模板与双模型协同：LLM 怎么接入本体建模

> 本篇是「本体建模最佳实践」文档集第三篇。前置阅读：[第二篇 流水线落地](本体建模-02-流水线落地.md)（各阶段在哪里用这些模板）；本篇收拢全部提示词模板（A–G 七个）与「生成者/审计者」双模型协同的完整方法。
>
> 模板用法一句话：**模板是带 `【占位符】` 的长版原文，用 `.replace("【占位符】", 值)` 填充，`create_provider(...).generate(...)` 执行，`json.loads(...)` 解析**。

## 一、LLM 接入配置（先打通，再谈模板）

Semantica 的 LLM 接入走 OpenAI 兼容协议。**0.6.7 实测要点**（[StockInsight 踩坑实录](../../projects/StockInsight/GUIDE.md)）：

```python
import os
from semantica.semantic_extract.providers import create_provider

llm = create_provider("openai", model="glm-5.3-flash",
                      base_url="https://open.bigmodel.cn/api/coding/paas/v4",
                      api_key=os.environ["ZHIPU_API_KEY"])
text = llm.generate(prompt)                    # 普通生成 → JSON 字符串
obj  = llm.generate_typed(prompt, schema=...)  # 带 Pydantic 硬校验的生成
```

- `provider` 必须传 `"openai"` 字符串走兼容端点；抽取器实例参数 `llm_provider=` 在 0.6.7 不被识别。
- 智谱（GLM）唯一可用端点是 `https://open.bigmodel.cn/api/coding/paas/v4`；`api/paas/v4` 报余额不足、`api/v1` 报无权限。
- key 走环境变量（`ZHIPU_API_KEY` / `DEEPSEEK_API_KEY` / `MOONSHOT_API_KEY` / `OPENAI_API_KEY`），存项目级 `.env`（权限 600），脚本 `load_dotenv` 读取，不回显不提交。
- 结构化输出用 `generate_typed(prompt, schema=EntitiesResponse)` 走 Pydantic 硬校验，坏输出当场抛错，不要裸 `generate` 后手写容错。
- **schema 不限于库内置类型**：任意自定义 `pydantic.BaseModel` 直接传给 `schema=` 同样生效（StockInsight 流水线实测：自定义三段抽取 schema + `Optional` 字段带默认、类型错即拒；见 `projects/StockInsight/scripts/_extract_core.py`）。
- **环境没装 instructor 时 `generate_typed` 依然可用**：0.6.7 会退化到库内 manual repair loop——`generate()` 产出 JSON 后 `schema.model_validate()` 字段级校验，校验失败把错误摘要回灌 prompt 自动重试；坏输出照样抛 `ValidationError`，不会静默放行（同上实测）。两条路径的硬校验力度一致，差别只在修复环的实现。

**为什么用 `.replace()` 不用 `.format()`**：模板里的 JSON 花括号 `{}` 会被 `.format()` 当占位符吞掉；`.replace("【占位符】", 值)` 中文方括号占位符与 JSON 语法零冲突。

## 二、七个模板（A–G）集中管理

模板正文集中在本篇，正文（第二篇）只给调用方式。每个模板都遵循同一骨架：角色 → 任务 → 输入 → 输出骨架（严格 JSON）→ 纪律约束。这套四段式源自[书稿 6.2.1 的 Prompt 规范](book/ontology-modeling-ch6-2-modeling.md)（角色与任务/输入/输出格式/质量规范）。

### A 实体与三元组抽取（用在 3.2 语义标准化）

```python
ENT_TEMPLATE = """【角色】你是 Semantica 的语义抽取器。只从下面文本抽取命名实体。
【输出】只输出 JSON：{"entities": [{"text": "<实体原文>", "label": "<类型>", "confidence": 0.95}]}
【约束】实体必须是文本中的原文子串；不要臆造；不确定就省略；type 用业务分类。
【业务文本】【业务文本】"""

TRIP_TEMPLATE = """【角色】你是三元组抽取器。从文本抽 (主语,谓语,宾语) 三元组。
【输出】只输出 JSON：{"triplets": [{"subject": "<原文子串>", "predicate": "<关系>", "object": "<原文子串>", "confidence": 0.9, "metadata": {"source": "<原文片段>"}}]}
【约束】subject/object 必须是原文子串；谓语对齐语义标准；来源写进 metadata.source。
【业务文本】【业务文本】"""

from semantica.semantic_extract.schemas import EntitiesResponse, TripletsResponse
ents    = llm.generate_typed(ENT_TEMPLATE.replace("【业务文本】", text), schema=EntitiesResponse)
triples = llm.generate_typed(TRIP_TEMPLATE.replace("【业务文本】", text), schema=TripletsResponse)
```

要点：只输出 `text/label/confidence` 三字段——LLM 给不准字符偏移，偏移由库回文本反查；事件不塞进三元组，单独走 `EventDetector`。

### B 术语归一与本体细化（用在 3.3 术语归一）

```python
B_TEMPLATE = """【角色】你是 Semantica 的本体细化器。基于原始对象清单，输出 Semantica 原生 ontology 字典（classes/properties），并给出术语去重表。
【任务】把对象归成类；每个类给 name/label/comment/parent/uri；对象的属性给成 property（type=object|data, domain, range）。

【输入】
- 原始对象清单： 【对象清单】
- 术语表： 【术语表】

【输出骨架（严格按此结构）】
{
  "name": "<本体名>",
  "base_uri": "https://example.org/ontology/",
  "classes": [
    {"name": "<类名>", "label": "<标签>", "comment": "<注释>", "parent": "<父类名或空>", "uri": "<IRI或空>"}
  ],
  "properties": [
    {"name": "<属性名>", "type": "object|data", "domain": ["<类名>"], "range": ["<类名|xsd:string>"], "label": "<标签>", "comment": "<注释>", "uri": "<IRI或空>"}
  ],
  "term_normalization": [
    {"canonical": "<规范名>", "aliases": ["<别名>"], "action": "merge|split", "confidence": 0.9}
  ],
  "equivalents": [{"a": "<类名>", "b": "<类名>"}],
  "disjoints": [{"a": "<类名>", "b": "<类名>"}]
}

【输出】只输出上述 JSON，不要附解释。"""

prompt = B_TEMPLATE.replace("【对象清单】", json.dumps(objects, ensure_ascii=False)).replace("【术语表】", "")
data = json.loads(llm.generate(prompt))
# 产物去向：term_normalization → 别名词表（人工确认后并入 alias_map）；
#           classes/properties → 与 D 模板产物合并后走 to_owl（不是 from_data，见 D）
```

### C 业务规则生成（用在 3.6 规则推理）

```python
C_TEMPLATE = """【角色】你是 Semantica 的业务规则建模器。
【任务】把业务规则翻译成 Semantica Reasoner 能直接吃下的规则字符串。

【输出骨架（严格按此结构）】
{
  "rules": [
    "IF <条件原子> AND <条件原子> THEN <结论原子>"
  ],
  "rules_conflicts": [
    {"a": "<规则序号>", "b": "<规则序号>", "resolution": "<谁优先>"}
  ],
  "unclear_rules": ["<语义含混的规则>"]
}

【规则语法铁律（必须遵守）】
- 每条规则是单行字符串：IF <条件> AND <条件> THEN <结论>（AND 连接条件，THEN 后是结论）。
- 原子形如 Predicate(arg1, arg2)，变量用 ?x 形式，常量直接写。
- 例：IF gross_margin_declining(?c) AND loss_widening(?c) THEN hold_and_monitor(?c)
- 不要用 -> 或 => 箭头；不要输出 ODRL（Semantica 无 ODRL 解释器，权限用规则近似，见第四篇）。
【输入】规则清单： 【规则清单】
【输出】只输出上述 JSON，不要附解释。"""

rules = json.loads(llm.generate(C_TEMPLATE.replace("【规则清单】", "毛利率连续下滑且亏损扩大则持有观察；投资决策需复核人批准")))
for rule_str in rules["rules"]:
    r.add_rule(rule_str)                 # 直接喂给 Reasoner，无需再转换
```

语法铁律的依据：`Reasoner._parse_rule_definition` 只认 `IF ... THEN ...`，**不匹配的规则会被静默解析成永不触发的空条件规则**——模板里把铁律写死，就是为了在生成侧挡住这个静默失败。

### D 本体生成器（用在 3.5 本体建模，注入版）

```python
D_TEMPLATE = """【角色】你是大模型 A —— Semantica 的本体生成器。你的职责是把"标准化业务语义描述"转成 Semantica 原生 ontology 字典（classes/properties）。
【约束】你是转译器，不是创作者：不要新增业务含义、不要编造术语。Turtle 不要你来写（由 to_owl 生成）。

【输入】
- 标准化描述（29 句话的实例化产出）： 【标准化描述】
- 术语表（概念 → IRI/命名空间）： 【术语表】
- 目标命名空间前缀： 【前缀映射】

【输出骨架（严格按此结构）】
{
  "name": "<本体名>",
  "base_uri": "https://example.org/ontology/",
  "classes": [
    {"name": "<类名>", "label": "<标签>", "comment": "<注释>", "parent": "<父类名>", "uri": "<IRI>"}
  ],
  "properties": [
    {"name": "<属性名>", "type": "object|data", "domain": ["<类名>"], "range": ["<类名|xsd:string>"], "label": "<标签>", "comment": "<注释>", "uri": "<IRI>"}
  ],
  "issues": [{"type": "待澄清|命名冲突|缺术语", "detail": "<说明>", "severity": "info|warning|error"}]
}

【输出】只输出上述 JSON，不要附解释。"""

prompt = D_TEMPLATE.replace("【标准化描述】", desc).replace("【术语表】", glossary).replace("【前缀映射】", "https://example.org/ontology/")
data = json.loads(llm.generate(prompt))

# 关键一步（0.6.7 实装行为）：注入版不走 from_data（它只认 entities/relationships），
# 而是规范 uri 键后直接喂 to_owl——to_owl 读 ontology.get("uri")
data["uri"] = data.pop("base_uri")
turtle = engine.to_owl(data, format="turtle")   # Turtle 由库确定性生成，不让 LLM 写
```

### E 独立审计器（用在 3.6 审计，双模型协同中的 B 角色）

```python
E_TEMPLATE = """【角色】你是大模型 B —— Semantica 的独立审计器。你不参与生成，只对 A 产出的本体做验收审计。
【任务】对输入的本体文本做四维审计，并按严重程度（error / warning / info）输出有序问题清单。

【输入】
- 待审本体（A 的输出）： 【待审本体】（Turtle/OWL）
- 原始标准描述： 【标准化描述】
- 术语表/命名空间约定： 【术语表】
- 目标标准： 【目标标准】（默认 RDF + OWL 2）

【四维审计】
1. 语法与标准合规：Turtle 是否能解析？前缀是否声明？是否用了非 W3C 词汇？命名是否合规？
2. 逻辑一致性：是否存在 disjointWith 与 subClassOf 矛盾、等价类冲突、循环 subClassOf、一个实例同时是两个互斥类成员？推理后是否矛盾？
3. 语义归一：是否出现"同概念多个 IRI、一词多用、多词一义、命名漂移"？是否复用术语表规范 IRI？
4. 业务落地：原标准描述里每个关键对象/关系/事件/属性是否都体现在本体里？是否有本体引入但源里不存在的业务含义？

【输出骨架（严格按此结构，按 severity 从高到低排序）】
{
  "verdict": "pass|needs_rework|fail",
  "issues": [
    {"id": "<I_编号>", "dimension": "syntax|consistency|normalization|business_grounding", "severity": "error|warning|info", "location": "<本体中的位置/IRI/三元组>", "description": "<问题描述>", "suggestion": "<建议修法>", "evidence": "<证据或推理说明>"}
  ],
  "summary": "<总体评价>"
}

【审计纪律】每个问题都给出证据与可执行修法；会导致解析失败/推理矛盾=error，语义错误/业务偏差=warning，可优化/命名建议=info；你只产问题清单，不修改本体。
【输出】只输出上述 JSON，不要附解释。"""

audit = json.loads(llm.generate(E_TEMPLATE.replace("【待审本体】", turtle)))
```

四维中的前三维对应[书稿 6.2.2 审计者 Prompt](book/ontology-modeling-ch6-2-modeling.md) 的三维度（语法与规范性/逻辑一致性/业务贴合度），第四维「语义归一」是工程扩展——LLM 生成最常见的病是术语漂移。

> **工程注记（StockInsight 流水线实测）**：审计对象是「抽取产物」而非本体时，模板 E 的输入位【标准化描述】/【术语表】应换成**生成侧提示词条款**（抽取规范原文：简体统一条款、自称替换条款、类型/事件受控词表、id 规范化规则）。否则审计者按一般直觉判级，会把源头治理条款本身当成缺陷——例如把「閆俊傑照转简体为闫俊杰」判成繁简混用 error，引发无意义回滚循环；生成者的辩护 Prompt 也要显式声明「符合规范的行为必须 defend 而非 revise」。

### F 可视化评审引导（用在 3.7 建图与校验的专家把关）

```python
F_TEMPLATE = """【角色】你是 Semantica 的可视化与评审引导器。你把本体/图谱转换成一棵/一张适合非技术领域专家阅读的图，并给评审人员一份傻瓜式的校验清单。

【输入】
- 待评审本体/图谱： 【待评审图谱】
- 术语表（用人类语言解释概念，给非专家看）： 【术语表】
- 评审人身份与关注点： 【评审人】+【评审关注点】

【你要产出的】
1. 可视化示意：用 Mermaid（graph TD / classDiagram）或 ASCII 树，把"类 + 关键关系 + 示例实例"画成一张图，用中文/业务语言标注节点与连线，高亮主概念、子概念、关键对象关系。
2. 评审引导词：给评审人 30 秒背景说明。
3. 校验清单（逐项打勾）：类完整性（是否覆盖所有关键事物类别，有无漏/多）；对象链接正确性（关系方向与语义是否正确，有无连错/颠倒/漏连）；属性有效性（属性是否真实、必要，有无挂错对象或缺失）。
4. 采集反馈：每个校验点给"是/否/不确定"判定并一句话说明问题。

【输出骨架（严格按此结构）】
{
  "graph_diagram_mermaid": "<可渲染的 mermaid 代码块>",
  "reviewer_brief": "<给评审人的背景说明>",
  "checklist": [
    {"item": "<类完整性|对象链接|属性有效性>", "prompt": "<提问>", "expected": "<期望正确表现>", "verdict": "是|否|不确定", "note": "<评审人备注>", "affected_entities": ["<涉及实体>"]}
  ],
  "review_summary": {"missing_classes": ["<缺失类>"], "wrong_links": ["<连错关系>"], "bad_properties": ["<属性问题>"], "approved": "是|需修改"}
}

【自检约束】可视化是否"非专家可懂"？校验问题是否面向业务正确性而非技术正确性？
【输出】只输出上述 JSON，不要附解释。"""

prompt = F_TEMPLATE.replace("【待评审图谱】", json.dumps(graph, ensure_ascii=False)).replace("【评审人】", "投资经理").replace("【评审关注点】", "持仓公司与财务指标的关联")
review = json.loads(llm.generate(prompt))
```

注意分工：**确定性渲染用 `KGVisualizer`**（交互 HTML），本模板产的是「给专家看的简化示意图 + 评审清单」——两者互补，不是替代（LLM 画图不具备确定性，不能当唯一可视化）。

### G 测试用例生成（用在 3.8 场景测试的 AI 矩阵）

```python
G_TEMPLATE = """【角色】你是 Semantica 的推理测试用例设计器。你基于给定的本体、规则与流程，针对一个具体业务场景，设计能验证"推理与查询是否正确"的测试用例。

【输入】
- 本体/规则/流程： 【本体与规则】
- 场景描述： 【场景描述】
- 术语表/命名空间： 【术语表】

【你要产出的测试用例（每条四要素）】
1. 场景设置（setup）：为测试准备的最小事实集（一组"已知为真"的实例/三元组/事实）。
2. 查询或触发：要执行的查询（SPARQL）或要触发的规则（Reasoner IF-THEN / Datalog 子句）。
3. 期望结果（expected）：在正确推理下应该得到什么。
4. 判定方式（assert）：如何判定测试通过。

【用例设计原则】
- 正例（该会的会）、负例（不该的不该）、边界（临界值）、组合/冲突（多规则优先级）、反直觉（会不会把不该发生的当成发生）。
- 每条用例给出覆盖的语义点（哪个规则/类/关系），并给 2~3 条反直觉用例。

【输出骨架（严格按此结构）】
{
  "scenario": "<一句话概括>",
  "test_cases": [
    {"id": "<TC_编号>", "type": "positive|negative|boundary|conflict|tricky", "setup_facts": ["<最小事实集>"], "query_or_trigger": {"kind": "sparql|reasoner|datalog", "content": "<要执行的东西>"}, "expected": "<期望输出>", "assert": {"condition": "<断言条件>", "detail": "<判断依据>"}, "covers": ["<覆盖的规则/类/关系>"], "rationale": "<为何得到该期望结果>"}
  ],
  "insufficient": ["<当前本体/规则/流程不足以判定的点>"]
}

【自检约束】每条用例 setup 是否最小且无歧义？期望结果是否唯一可判定？是否覆盖正/负/边界/冲突/反直觉五类？
【输出】只输出上述 JSON，不要附解释。"""

cases = json.loads(llm.generate(G_TEMPLATE.replace("【本体与规则】", turtle).replace("【场景描述】", "MiniMax 2026H1 业绩与持仓策略")))
```

触发器只写 `sparql|reasoner|datalog`——Semantica 能执行的就这三种；SWRL/ODRL 是书稿目标标准，无执行引擎（见[第四篇](本体建模-04-能力边界与替代方案.md)）。

## 三、内置模板 vs 自建模板：异同与优劣

**抽取层**（`NERExtractor(method="llm")` 内置提示词 vs 模板 A）：

| 维度 | 内置 | 模板 A |
|---|---|---|
| 输出 | 库原生 schema | 同原生 schema（`generate_typed` 硬校验）+ 事件/溯源扩展 |
| 结构校验 | 库内建 | Pydantic 硬校验，坏输出当场抛错 |
| 事件/溯源 | 无事件；溯源靠后补 | 事件走 `EventDetector`；来源进 `metadata.source` |
| 优劣 | 优：短/快/省；劣：维度少 | 优：维度全；劣：更长 |

**建模层**（`OntologyEngine.from_text` 内置 vs 模板 D）：

| 维度 | 内置 from_text | 模板 D |
|---|---|---|
| 输入 | 裸文本 | 29 句话实例化描述 + 术语表（受控输入） |
| 输出 | 本体 dict（内部已做 base_uri→uri 规范） | 同构本体 dict + issues 清单；**入库路径不同**（见下） |
| 入库 | `from_text` 链路内闭环 | `data["uri"]=...` 后直接 `to_owl`（不走 `from_data`） |
| 优劣 | 优：一行搞定；劣：输入不受控、无 issues | 优：受控、可审计；劣：多两步 |

**结论**：内置适合「快省」探索，自建模板适合「细全」生产，互补不替代。共同纪律：**Turtle 永远由 `to_owl` 确定性生成，不让 LLM 手写**。

## 四、双大模型协同：生成、审计、仲裁的闭环

「双大模型协同」在本文档集里只有一个定义：**大模型 A（本体转化生成者）+ 大模型 B（审计者）的异构协同**（[书稿 6.2.2](book/ontology-modeling-ch6-2-modeling.md)）。它解决的矛盾是：单一大模型难以兼顾「逻辑生成」与「严苛审核」——生成者和审计者需要的模型特长相反。

### 角色分工（书稿表 6-3）

| 分工维度 | 大模型 A：本体转化生成者 | 大模型 B：审计者 |
|---|---|---|
| 核心角色 | 语义重构与编码转换 | 逻辑校验与合规审查 |
| 主要任务 | 29 句话描述 → OWL/RDF 语法；建类层级；写推理规则 | 静态语法扫描；逻辑自洽检查（类重叠/规则冲突）；规范对齐核对 |
| 选型偏好 | 业务逻辑理解力强、上下文处理能力强 | 推理逻辑严密、遵循指令度极高（逻辑/数学评测突出者） |
| 输出 | 初版本体模型文件 | 《本体语义缺陷报告》（严重级别–问题–位置–建议） |
| 协同策略 | 接收 B 的反馈，修正直至达到审计要求 | 「黑盒测试」思维，不断挑战 A 的逻辑漏洞 |

### 三步闭环

1. **交叉互审**：A 按模板 D 生成本体；B 按模板 E 独立审计（A 的本体 + 原始 29 句话描述都在 B 的输入里——B 审的是「译文是否忠于原文」）。
2. **逻辑博弈**：B 的缺陷报告同步给 A。A 对每条质疑二选一——确有错误直接修正；认为审计有误则给出基于业务描述和本体规范的逻辑辩护。产出修订版 + 《辩护与修订说明》。

   ```python
   DEFENSE_TEMPLATE = """你收到了审计报告。请逐一审查所有问题：
   1) 对于确实存在的错误，直接修正本体；
   2) 对于认为审计有误的质疑，提供基于业务描述和本体规范的逻辑辩护理由。
   请输出修订后的本体 V2.0，并附上一份"辩护与修订说明"。"""
   ```

3. **专家共识与最终仲裁**：结论一致则自动通过；核心规则有争议，提取分歧点推送人工终审（业务专家 + 工程师裁决）。仲裁结果进 3.9 的决策记录。

### 大模型选型五维法（书稿表 6-2）

| 选型维度 | 核心评价指标 | 验证方法 |
|---|---|---|
| W3C 规范理解力 | RDF/OWL/SKOS 语法掌握程度 | 本体转译测试：业务逻辑 → Turtle/Markdown，查语法完整性 |
| 语义逻辑推理 | 类继承、属性传递推导隐含关系 | 隐性关系推导：A⊂B、B⊂C，问 A 是否 C 的实例 |
| 模式合规性校验 | 主动发现 Domain/Range 冲突等违约 | 反例识别：给错误的 OWL 逻辑，看能否指出冲突 |
| 多层级语义对齐 | 区分公共层/领域层/实例层 | 层级分类测试：「合同/借款合同/合同编号 001」归类 |
| 领域知识覆盖 | 行业标准术语与业务俗称的对应 | 术语库对齐提问 |

选 A 侧重前三行的「懂标准、会推理」，选 B 侧重「严合规、指令遵从」——两个模型最好来自不同技术路线（异构协同），共享盲区的概率更低。
