# 能力边界与替代方案：书稿目标标准 vs Semantica 实际实现

> 本篇是「本体建模最佳实践」文档集第四篇。前置阅读：[第一篇 总纲](本体建模最佳实践.md)（书稿方法论的七类语义）。
>
> 书稿的方法论建立在 W3C 全家桶上（RDF/OWL/SKOS/SWRL/SPARQL/OWL-S/ODRL），但 Semantica 是这条标准栈的**子集实现**。把「书稿要求的标准」当成「库里已有的能力」，是踩坑的最大来源。本篇给出每一项差距的证据位置与可行替代，让「知道没有」和「知道怎么绕」一样明确。

## 一、版本基准与裁定规则

本文件集全部 API 表述基于 **Semantica 0.6.7**（`.venv` 实装），而官方文档（[quickstart](../quickstart.md) 等）标注 **0.5.0**——文档滞后于实装。遇到分歧时按以下优先级裁定：

```
StockInsight 实测调用（0.6.7 跑通） > docs/reference/*.md > docs/concepts / quickstart / modules
```

例如：`detect_conflicts(graph)` 这个类方法签名 reference 未载，但 0.6.7 实测可用（[StockInsight build_full_graph.py](../../projects/StockInsight/scripts/build_full_graph.py)）；反过来 concepts.md 的部分 API 名在 reference 与实装中都不存在（见第三节裁定表）。

## 二、目标标准 vs 实际实现：差距清单

| 书稿目标标准 | 29 句话落点 | Semantica 实况（0.6.7） | 证据位置 | 可行替代 |
|---|---|---|---|---|
| SWRL（规则） | 第 4 类业务控制规则 | **无 SWRL 实现**（全库 grep 无 swrl:Imp 处理） | `semantica/` 全包 | `Reasoner` 的 `IF…AND…THEN` 规则字符串 / `DatalogReasoner` Horn 子句 |
| OWL-S（流程服务） | 第 5 类流程活动 | **无 OWL-S 实现** | 全包 grep | 事件抽取（`EventDetector`）+ 规则近似流程触发 |
| ODRL（权限管控） | 第 6 类权限管控 | **无 ODRL 解释器、无 RBAC/ABAC 引擎、无 per-triplet ACL** | 全包 grep + [7.1 考察](#三权限odrl的五处影子方案) | 三层近似（见下节） |
| OWL 属性逻辑特征（函数/反函数/传递/逆，即「四剑客」） | 2.x 分层约束 | **无任何处理**：全库无 `FunctionalProperty` 等四种约束的实现，`to_shacl` 也不生成 | `semantica/ontology/` 全模块 grep | 设计侧人工保证唯一性（业务键 ID）；校验侧用 SHACL `minCount/maxCount` 近似 + `GraphValidator(schema=)` 类型词汇校验 |
| TEMPORAL / LOGICAL 冲突检测 | 第 2 类约束（值随时间） | `ConflictDetector` **仅实现** value/type/relationship/entity 四法；TEMPORAL/LOGICAL 只是枚举占位 | [conflicts 参考](../reference/conflicts.md) Warning 原文 | 时态数据走 `kg` 时态查询（`valid_from/valid_to`），冲突用 value 法按 `property_name` 分时段检测 |
| PROV-O 序列化 | 溯源 | 溯源记录本身完整（PROV-O 兼容），但 `ProvenanceManager` **无内置 Turtle/JSON-LD 序列化** | [provenance 参考](../reference/provenance.md) | RDF 导出带溯源：`RDFExporter(include_provenance=True)` |
| OWL 推理机（HermiT/Pellet/ELK） | 分层推导 | 本体可导出，**推理本身在 Semantica 之外运行** | [ontology 指南](../guides/ontology.md) | 库内推理用 `Reasoner`/`DatalogReasoner`；重推理需求导出 Turtle 到外部推理机 |

一个正反对照：第 2.2 节映射表中标 \* 的四行（SWRL/OWL-S/ODRL/四剑客）全部落在本表——它们在书稿里是「语义标准」，在 Semantica 里是「设计原则 + 替代实现」。

## 三、权限/ODRL 的五处影子方案

「权限」在代码库里散落五处，没有一处是数据级访问控制。如实列出（均已核实到代码位置）：

| 影子方案 | 代码位置 | 本质 |
|---|---|---|
| 认证 | `server.py` / `ingest/*` 的 `Authorization` header | 身份认证，非图权限 |
| 只读守卫 | `explorer/routes/sparql.py` 的 `_FORBIDDEN_KEYWORDS`（拦 INSERT/DELETE/DROP…） | 防滥用，非角色授权 |
| 决策留痕 | `context.ContextGraph.record_decision(...)` | 记录「谁批准/拒绝」，可追溯但**不拦截** |
| 通用规则 | `reasoning.Reasoner.add_rule("IF…THEN")` | 可建模 allowed/denied，非专用权限引擎 |
| 角色结构 | `ontology` 的 `create_position_class(...)` | 只建模「谁是什么角色」，无动作允许/禁止 |

**三层近似 ODRL**（规则当闸门 + 决策留痕 + 人工流程兜底）：

```python
from semantica.reasoning import Reasoner
from semantica.context import ContextGraph

r = Reasoner()
r.add_rule("IF Role(analyst) AND edit(analyst, strategy) THEN forbidden(analyst, strategy)")
r.add_rule("IF Role(pm) AND edit(pm, strategy) THEN allowed(pm, strategy)")

ContextGraph().record_decision(category="access_control",
    scenario="分析师修改持仓策略", reasoning="角色为 analyst，无编辑权限",
    outcome="denied", confidence=0.99, decision_maker="policy-engine")   # 留痕
```

## 四、官方文档内部不一致裁定表

官方文档自身有 11 处互相矛盾。引用任何 API 前先对一遍这张表（裁定原则：reference 为准，实测优先）：

| # | 写法 A | 写法 B | 裁定 |
|---|---|---|---|
| 1 | OntologyGenerator 6 阶段（guides/concepts） | 5 阶段（reference；源码 docstring 同 5） | 5 阶段（源码 [ontology_generator.py](../../semantica/ontology/ontology_generator.py) 为证） |
| 2 | `RuleType.FORWARD_CHAIN`（concepts） | `RuleType.IMPLICATION/EQUIVALENCE/CONSTRAINT/TRANSFORMATION`（reference） | 后者 |
| 3 | `DatalogEngine()`、`apply_transitivity/infer()`（modules） | `DatalogReasoner`、`derive_all/query`（reference） | 后者 |
| 4 | `prov.get_entity_lineage(...)`（concepts/quickstart） | `get_lineage/trace_lineage`（reference） | 后者 |
| 5 | `detector.detect_conflicts(kg)` + `detector.resolve(...)`（modules） | `ConflictDetector.detect_*` + `ConflictResolver.resolve_conflicts`（reference） | reference 签名为准；0.6.7 实测 `ConflictDetector().detect_conflicts(graph)` 也可用 |
| 6 | `context.analyze_decision_influence(id)`（concepts/quickstart）、`context.query(mode="graphrag")` | `trace_decision_explainability`、`retrieve/query_with_reasoning`（reference） | reference；`analyze_decision_influence` 在 0.6.7 实测存在（StockInsight pipeline_v3 调用过），标注「实测可用、reference 未载」 |
| 7 | `DocumentParser(ocr=True)`（quickstart） | OCR 走 `DoclingParser(enable_ocr=True)`（reference） | 后者 |
| 8 | 抽取方法名 `"ml"`（concepts/modules） | `"huggingface"`（reference 正文） | 实测 `method="llm"`/`"pattern"` 最稳；ml/huggingface 并存时以实际安装为准 |
| 9 | LLM provider 9 个（concepts）/ 8 个（modules） | guides：Groq/OpenAI/Anthropic/HuggingFace/Novita + LiteLLM 100+ | guides 口径 |
| 10 | `merge_duplicates` 返回实体列表（concepts 暗示） | 返回 `List[MergeOperation]`（reference 明确 Warning） | 后者（源码为证） |
| 11 | 解析产物正文键 `full_text`（reference/parse） | `parsed["text"]`（StockInsight 实测 0.6.7） | 兼容写法 `parsed.get("full_text") or parsed.get("text")` |

## 五、其他已知坑与替代

| 坑 | 现状 | 替代/规避 |
|---|---|---|
| SHACL 运行时验证缺依赖 | `validate_graph` 需要可选依赖 pyshacl，缺失时抛 ImportError | 安装 `uv pip install "semantica[shacl]"`；不装则只做 `GraphValidator` 结构校验 |
| 版本快照的 author 校验 | `TemporalVersionManager.create_snapshot` 的 author 必须是**邮箱格式**（ChangeLogEntry 校验），传人名抛 ValidationError | author 传邮箱；version_label 带时间戳避免重跑撞标签 |
| 冲突检测的分组键 | `detect_conflicts(method="value")` 按**实体 ID** 分组找多来源矛盾，同名不同 ID 不算冲突 | 归一阶段先把同实体统一到同一 ID（第二篇 3.3），再进冲突检测 |
| `merge_entities` 按**相似度**分组，不按 id | 同 id 的多来源记录（如同实体 99 条）只有相似的少数进合并组；若按「id 出现在 source_entities 即排除」来拼完整集，未进组的同 id 记录会被**静默丢弃** | 自己按规范 id 折叠（同 id 字段并集），跨 id 合并只走显式别名表；StockInsight 实测曾因此丢 97 条主实体记录 |
| `GraphBuilder(merge_entities=True)` 二次模糊合并 | 输入已去重时再开 merge_entities，会把「MiniMax Group Inc.」与「上海稀宇科技有限公司」这类**不同实体**模糊并组，合并产物还可能顶掉规范名 | 输入已按 id 折叠就传 `merge_entities=False`（默认值）；merge_entities 只用于未去重的原始多源输入 |
| 规则箭头 `->` / `=>` | `Reasoner` 只解析 `IF…THEN`；**不匹配的规则静默变成永不触发的空条件规则，不报错**（`_parse_rule_definition` 的 fallback） | 模板 C 把语法铁律写进提示词；入库后抽查 `r._rules` 长度与条件非空 |
| LLM 输出字符偏移不准 | LLM 给不准 `start/end` | 抽取只要 `text/label/confidence`，偏移由库回文本反查 |
| LLM 手写 Turtle 易错 | — | Turtle 永远由 `to_owl(dict)` 确定性生成 |
| `from_data` 不吃现成本体定义 | 只认 `entities/relationships`（数据推导） | 注入版规范 `uri` 键后直接 `to_owl`（第二篇 3.5） |
| `OntologyEngine()` 默认无 store | `create_alignment` 抛 `ProcessingError` | 先配置 `TripletStore` 再调对齐方法 |
| Parquet/Arrow 导出静默无效 | 缺 pyarrow 时导出器是 no-op stub | `uv pip install pyarrow` 后再导出；导出后断言文件存在 |
| 溯源默认内存存储 | `InMemoryStorage` 不跨进程 | `ProvenanceManager(storage_path="provenance.db")` |
| `GraphBuilder.build()` 返回 dict | `PathFinder`/`GraphAnalyzer` 要 networkx 图 | 先做 dict→DiGraph 转换（StockInsight graph_analytics.py 有标准写法） |
| FalkorDB 字符串 ID 不落库 | `create_node` 用数字内部 ID | 纯 Cypher + `name` 属性为键；返回 bytes 要 decode |
| Datalog 变量格式 | 官方文档写 `?X`，实装要**大写无前缀**（`X`/`Y`），常量小写开头 | 按实装写（StockInsight 实测） |
| `validate_ontology` 的判定强度 | 关键词启发式（类名/属性名含问题分词即 answerable） | answerable ≠ 推理链已通；推理验证在场景测试做（第二篇 3.8） |

## 六、能力边界使用守则

1. **选型前看第二节的表**：领域若强依赖 ODRL/SWRL/OWL-S 的原生执行，评估外部推理机或权限中间件，不要硬用近似方案承载合规责任。
2. **写文档/提示词时明示边界**：凡涉及目标标准的能力，表述为「按 X 标准设计、以 Y 方式落地」，不写「Semantica 支持 X」。
3. **升级时复核本篇**：本篇结论锚定 0.6.7；上游发版后优先回归第二篇附录的最小链路，再按第一节裁定规则复核。
