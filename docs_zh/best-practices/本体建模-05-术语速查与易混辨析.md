# 术语速查与易混辨析

> 本篇是「本体建模最佳实践」文档集第五篇（参考篇），随查随用。术语表是全文档集的用词规范：正文里术语首次出现处标注英文，后续统一用中文；「标准」列区分**目标标准**（书稿方法论设定）与**实际实现**（Semantica 0.6.7），详细对照见[第四篇](本体建模-04-能力边界与替代方案.md)。

## 一、术语速查（定义 · 模块 · 标准）

| 术语 | 一句话定义 | 模块 | 标准 |
|---|---|---|---|
| 本体（Ontology） | 一张共享的语义模型：对象、关系、动作的正式定义 | `ontology` | OWL（子集实现） |
| 显性知识（Explicit Knowledge） | 可写入文字/图表/编码、能直接被摄取解析的知识 | `ingest`/`parse`/`normalize`/`split`、`semantic_extract` | RDF |
| 隐性知识（Tacit Knowledge） | 藏在经验判断里、需专家访谈才能显性化的知识 | 29 句话访谈框架（篇1 2.3） | SKOS/OWL（目标标准） |
| 「29 句话」 | 把「7+1」语义规范细化的 29 种标准化描述模板，7 类语义组织 | 预处理的输出契约 | 书稿 6.1.1 图 6-1 |
| 业务-语义对齐 | 把业务口头术语一对一映射到本体类/属性/关系 | `ontology`、`semantic_extract` | SKOS（目标）、alias_map（实现） |
| 语义标准化描述模板 | 字段与语义固定的描述格式，同义同写法 | `normalize`、`semantic_extract`、`kg` | RDF/OWL |
| 双大模型协同 | 大模型 A（生成者）+ B（审计者）异构协同：交叉互审→逻辑博弈→仲裁 | LLM 编排（篇3 第四节） | 书稿 6.2.2 |
| 可视化校验 | 把本体/图图形化，按「拓扑→语义→规则回溯」三步人工核对 | `visualization`、`kg` | RDF/OWL 渲染 |
| 类层次 / 等价类 / 互斥类 | 父子分类树 / 同集合可互换 / 集合不相交 | `ontology`、`reasoning`、`conflicts` | RDFS/OWL |
| 术语去重（同物异名） | 合并同一概念的不同叫法 | `deduplication`、`normalize` | SKOS 首选/替代标签（目标）、alias_map（实现） |
| 业务规则 / 权限约束 | 业务须成立的「条件→动作」 vs 谁可对什么做什么 | `reasoning` / `reasoning`+`context` 近似 | SWRL（目标标准）/ ODRL（无实现） |
| 能力题（Competency Question, CQ） | 本体应该能回答的问题，建模的验收标准 | `CompetencyQuestionsManager` | — |
| 黄金测试用例 | 专家定义的核心场景+核心问题+预期结果 | 场景测试（篇2 3.8） | 书稿 6.2.4 |
| 溯源（Provenance） | 每条知识的来源、位置、原句、置信度全程可回查 | `provenance` | W3C PROV-O |
| 决策即一等对象（Decision as first-class object） | 判断被固化为可记录、可检索、可对比的决策对象 | `context` | — |
| 先例检索（Precedent Search） | 按场景检索历史相似决策 | `context`（`find_precedents`） | — |
| 冲突检测（Conflict Detection） | 标记多源事实的矛盾（先于合并执行） | `conflicts` | — |
| 去重（Deduplication） | 合并同一实体的重复表述（后于冲突消解执行） | `deduplication` | — |
| 种子数据（Seed Data） | 抽取前先入库的可信基础图（置信度 1.0） | `SeedDataManager`（cookbook 25） | — |
| 本体即代码（Ontology as Code） | 本体 dict 手写显式、与代码同版本化，不从 schema 推断 | `ontology`（cookbook advanced/13） | — |
| 关联类物化（Reification） | N 元事实用中间事件节点承载上下文（如雇佣关系带薪资时段） | `AssociativeClassBuilder` | OWL（目标）、快捷边双轨（实现） |

## 二、实体标识的三种形态与转换点

全流水线里「一个实体」有三种标识形态，转换点固定在两个地方——不知道这个，代码写着写着就会串：

| 形态 | 长相 | 出现阶段 | 转换点 |
|---|---|---|---|
| 原文子串 | `"MiniMax Group Inc."`（text + start/end 偏移） | 3.2 抽取产物 | — |
| 规范名 + 短 ID | `{"id": "e3", "name": "MiniMax Group Inc."}`（经 alias_map 归一） | 3.3 术语归一产物 | **转换点 1：3.3 的别名归一与合并** |
| 本体 IRI | `https://investment.example/ontology/Company` 类下的实例 IRI | 3.5 起的本体/图/导出 | **转换点 2：3.5 的命名空间管理（base_uri → uri）** |

## 三、易混点辨析

| 易混对 | 区别 |
|---|---|
| 对象 vs 类 | 个体实例 vs 类型；类用 `subClassOf` 组织，对象是类的实例 |
| 等价类 vs 互斥类 | 同义可互换（`equivalentClass`）vs 集合不相交（`disjointWith`） |
| 业务规则 vs 权限约束 | 条件→动作（SWRL 目标标准）vs 角色→可行动作（ODRL 目标标准，Semantica 无实现，近似方案见第四篇） |
| 抽取 vs 建模 | `semantic_extract` 抽事实（实例层）vs `ontology` 定结构（类/属性层） |
| 冲突检测 vs 去重 | `conflicts` 标记**矛盾**（同一属性两个值）vs `dedup` 合并**重复**（同一实体两种写法）；顺序铁律：先冲突后去重再建图 |
| `detect_duplicates` vs `dedup_triplets` | 前者检实体重复（返回候选对，供合并决策）；后者检三元组重复对——两者都是**检测**，都不是清洗，清洗要自己拿检测结果做合并 |
| `from_data` vs `to_owl` | `from_data` 从 entities/relationships **推导**本体；`to_owl` 把现成本体 dict **序列化**成 Turtle。注入版走后者（uri 键） |
| 双大模型协同 vs 混合检索表示 | 前者=生成者 LLM+审计者 LLM（本文档集唯一含义）；后者=语义层+向量层双表示（`AgentContext` 的 `use_graph` 检索），**两个概念，勿混用** |
| `validate_ontology`（独立函数）vs `validate_graph` | 前者查本体 dict 结构完整性（{valid/warnings/errors}）；后者做 SHACL 运行时验证（data_graph 须 RDF 字符串，shapes 由 ontology 自动生成） |
| `merge_entities` 的返回 | 返回 `List[MergeOperation]`（合并操作记录），**不是**实体列表；完整去重集要自己拼「合并产物 + 未参与合并的孤立实体」 |
| answerable ≠ 推得通 | CQ 的 answerable 是关键词启发式判定；真正的推理验证要靠场景测试的断言（backward_chain） |
