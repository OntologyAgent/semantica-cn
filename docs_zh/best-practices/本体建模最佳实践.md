# 本体建模总纲与知识契约：把业务知识沉淀为可复用的本体资产

> 本篇是「本体建模最佳实践」文档集的第一篇（总纲）。整套方法回答一个问题：**如何可靠地把业务知识沉淀为可复用、可验证、可审计的本体资产**。
>
> 方法论主干源自《低门槛快速落地的本体建模工程化方法》第六章（[6.1 预处理](book/ontology-modeling-ch6-1-preprocessing.md)、[6.2 建模](book/ontology-modeling-ch6-2-modeling.md)），工程落地部分对齐 Semantica 0.6.7 实装与 [projects/StockInsight](../../projects/StockInsight/GUIDE.md) 真实财报案例的已验证调用。方法论与具体领域解耦——示例用投资领域，换到制造、医疗、法律同样成立（每阶段的适配指引见[第二篇](本体建模-02-流水线落地.md)）。
>
> **一条主线贯穿全文档集**：先建本体（Ontology），再记决策（Decision），终成回路（The Loop）。

## 一、全局视图：五环联动与九阶段落地

书稿把企业本体工程概括为**五环联动**：预处理 → 建模 → 入库 → 平台 → 实施，目标是让本体资产从「能建」迈向「可用、可管、可运营」（[书稿 6 章引言](book/ontology-modeling-ch6-1-preprocessing.md)）。落到 Semantica 上，前两环展开为一条可执行的流水线，后三环对应资产入库与下游消费。

下面这张表是整套方法的地图：左半边是书稿方法论的阶段划分，右半边是 Semantica 流水线的真实模块。后面每一篇都在为这张表添细节。

| 阶段 | 干什么 | 书稿方法论对应 | Semantica 模块 | 产物 |
|---|---|---|---|---|
| 1 多源萃取 | 异构原料拿回、解析、规范化、分块、带来源 | 预处理·显性知识提炼 | `ingest` `parse` `normalize` `split` | 带来源的分块（chunks） |
| 2 语义标准化 | 把业务文本抽成类型化实体/关系/事件 | 预处理·显性知识提炼 | `semantic_extract` | entities / relationships / events |
| 3 术语归一 | 同物异名合并、指代消解、入词表 | 预处理·隐性知识萃取（对象维度） | `normalize` `semantic_extract` `deduplication` | 规范化实体集 + 别名词表 |
| 4 冲突去重 | 先标记冲突再消解，最后去重 | 预处理·审核（逻辑正确） | `conflicts` → `deduplication` | 无静默覆盖的干净集 |
| 5 本体建模 | 建类层次/属性/术语/规则 | 建模·AI 精准建模 | `ontology` | 本体 dict + Turtle/SHACL |
| 6 规则推理与审计 | 条件→动作推导，独立审计把关 | 建模·双大模型协同 | `reasoning` | 推理信号 + 审计报告 |
| 7 建图与校验 | 合并建图、结构校验、SHACL 验证、可视化审 | 建模·可视化审核 | `kg` `ontology`(SHACL) `visualization` | 校验通过的知识图谱 |
| 8 场景测试 | 黄金用例 + 测试矩阵验证 | 建模·场景化测试 | `reasoning` + `ontology`(CQ) | 测试报告 + 回归用例集 |
| 9 资产入库 | 溯源、决策记录、版本、导出 | 入库环 | `provenance` `context` `export` | 可回滚、可导出的资产 |

理解这张表的关键，是看到它**不是单向流水线**：第 8 阶段测试失败会按「模型缺陷/用例错误/规则冲突」三分类退回第 5–7 阶段；第 4 阶段冲突检测必须在合并建图**之前**，图里合并后原始来源归属会丢失（[conflicts 参考](../reference/conflicts.md)：Detect before you merge, not after）。

## 二、输出契约：29 句话，让业务把「为什么」说清楚

有了全局视图，接下来的核心问题是：**业务知识长什么样，机器才读得懂？**

书稿的答案是「29 句话」范式：把「7+1」语义规范细化为 **29 种标准化自然语言描述模板**，按 7 类语义组织。它如同一位「翻译官」，把模糊的业务叙述转译为机器可读的本体语义单元（[书稿 6.1.1](book/ontology-modeling-ch6-1-preprocessing.md)）。

这份契约有双重的工程身份，在流水线里各就各位：

1. **抽取目标清单**——喂给 LLM 让它按类去抽，而不是自由发挥（第二篇 3.2 阶段）；
2. **能力题（Competency Questions）**——注册给 `CompetencyQuestionsManager`，建模完成后逐条验收本体能否作答（第二篇 3.5/3.8 阶段）。

### 2.2 七类语义与 Semantica 的对应

7 类语义各有落点。注意表中标 \* 的是**书稿设定的目标标准**，Semantica 尚无对应实现，落地时用右列的替代——完整对照见[第四篇](本体建模-04-能力边界与替代方案.md)。

| 语义类 | 29 句话落点 | Semantica 模块 | 标准与实现 |
|---|---|---|---|
| ① 业务对象描述 | 1.1/1.2 → 实体属性与关系抽取 | `semantic_extract` | RDF 语义，实现齐全 |
| ② 业务分层约束 | 2.1–2.7 → 类层次、domain/range、值约束 | `ontology` | OWL 子集，实现齐全 |
| ③ 业务术语 | 3.1–3.3 → 别名词表、消解合并 | `normalize` + `deduplication` | SKOS 目标，用 alias_map 近似 |
| ④ 业务控制规则 | 4.1 → IF…THEN 规则 | `reasoning` | SWRL* 目标，用 Reasoner 规则字符串 |
| ⑤ 流程活动与操作 | 5.1–5.5 → 事件与流程 | `semantic_extract`(Event) + `context` | OWL-S* 目标，用事件抽取+规则近似 |
| ⑥ 权限管控 | 6.1–6.4 → 角色与动作约束 | `reasoning` + `context` | ODRL* 目标，无实现，三层近似 |
| ⑦ CRUD 数据操作 | 7.1–7.7 → 查询与更新 | `triplet_store`(SPARQL) + `kg` | SPARQL 语义，实现齐全 |

### 2.3 隐性知识：29 句话的另一头

29 句话不仅用来消化**显性知识**（业务表单、流程图表、操作手册——AI 可直接摄取），还是萃取**隐性知识**的访谈框架。书稿 6.1.2 给出三维度问法（[原文](book/ontology-modeling-ch6-1-preprocessing.md)）：

- **有哪些对象**：按 SKOS 统一术语（首选/替代标签）、按 RDF 定义对象属性、按 OWL 划分「公共层–领域层–实例层」；
- **任务怎么做**：拆解原子动作并建立动作—对象关联，明确数据操作逻辑；
- **有哪些规则**：用「如果…那么…」显性化控制规则，界定各层级语义边界，界定角色权限。

每一维的产出都汇入 29 句话的对应类目。工程上的对应动作：对象维度落在阶段 3（术语归一），任务维度落在阶段 2（事件抽取）与阶段 6（规则），规则维度落在阶段 5–6。

## 三、质量准入：四条铁律

任何业务知识描述在进入本体建模之前，必须同时通过以下四条铁律。这四条直接对应书稿 6.1.3 的建模准入标准（[原文](book/ontology-modeling-ch6-1-preprocessing.md)）：描述清晰、逻辑正确、内容完备、极简表达。任一不过，即驳回，退回对应前置阶段修复，不允许在建模环节打补丁。

**P1 描述清晰**（书稿：术语全局唯一，精准对齐语义模板 → 退回阶段 2/3）

- [ ] 术语全局唯一；同一概念无多别名反复出现
- [ ] 字段/结构对齐标准描述模板，无自由发挥
- [ ] 核心概念有规范名与唯一标识（首选用规范化实体集的 IRI/ID）
- [ ] 命名合规（大小写/命名空间/驼峰下划线约定）
- [ ] 与 `semantic_extract` 输出一一对应，无「抽不到却写了」的孤儿表述
- [ ] 无「大概/可能/相关」等无法落到类/属性/值的模糊词

> 失败处理：建别名映射（阶段 3）；按命名规则重命名；改确定性表述；抽不到的先修抽取再评审。

**P2 逻辑正确**（书稿：分类清晰、规则无闭环冲突 → 退回阶段 3/4/5）

- [ ] 类/规则/动作三类被明确区分（不把动作当规则、把规则当类目）
- [ ] 层次分明，无跨层跳级、无循环继承
- [ ] 规则无触发闭环（A→B、B→A）；冲突检测先于去重、去重先于建图（阶段 4 → 阶段 7 的顺序铁律）
- [ ] 无自相矛盾（同一条件既真又假）
- [ ] 可被 `reasoning` 正确解读推出结论，无悬空规则

> 失败处理：重分类；重建层级消除循环；定位冲突环明确优先级；删除矛盾断言；不可推断则拒绝。

**P3 内容完备**（书稿：能串联「AI Agent 意图→事实–事理–行动」完整逻辑链 → 退回阶段 1/2/6）

- [ ] 每条描述锚定一个明确的 Agent 意图
- [ ] 支撑意图的事实齐备且可回查来源
- [ ] 事实→动作推理链完整，无「事实在、动作无 / 动作在、依据缺」断档
- [ ] 每环有 W3C PROV-O 溯源；关键决策经 `record_decision` 记录（阶段 9）
- [ ] 结论/动作都有对应事实或规则支撑，无凭空断言

> 失败处理：补意图、回阶段 1/2 补事实；补推理规则；补记 `record_decision`；断链禁止准入。

**P4 极简表达**（书稿：上下文精简精准、无冗余 → 退回阶段 3/4）

- [ ] 同一事实/规则/动作未重复表述
- [ ] 只含满足意图与推理的最小信息集，无多余属性/字段
- [ ] 无与意图无关的背景、注水内容
- [ ] 聚焦主意图，无过度发散
- [ ] 无零引用、不入链的孤立描述

> 失败处理：删重复；裁剪到最小集；剥离噪音；收敛孤立描述（`dedup`/`context`）。

**评审路径**（书稿 6.1.3 协同评审的工程化）：

```
建模工程师初审（P1、P4 形式层面，对照术语表与模板）
    → 领域专家复核（P2、P3 语义/闭环层面）
    → 不一致提交仲裁
    → 任一驳回即退回对应阶段（括号内标号）重走
```

四条铁律是准入门槛；两把日常尺子（属性约束校验、术语速查）收在[第五篇](本体建模-05-术语速查与易混辨析.md)。

## 四、结语：本体与决策回路

前面讲的是「怎么做」，这里回答「为什么这么做」——整套方法论的底层逻辑收敛成一条主线：**先建本体（Ontology），再用本体支撑决策（Decision），最后让决策积累成回路（The Loop）**。

### 为什么「回路」离不开「本体」

判断一家企业「该不该做某事」，本质上是一次决策；但决策要能被记录、追溯、对比，前提是决策所依赖的「对象、关系、动作」先有一张**共享的语义模型**。没有本体，决策就是一句散落在邮件里的口头判断——既回查不了，也复用不了。29 句话把业务知识规范成七类语义，建的就是这张共享模型。

### 把回路拆成三层

| 环节 | 我们做的事 | 对应的能力 |
|---|---|---|
| 本体层（静态模型） | 抽取七类语义、建类/属性/等价/互斥 | 对象、关系、事件、属性、术语、规则、权限 |
| 决策层（动作） | `record_decision` 把判断固化成决策对象 | 决策即一等对象（Decision as first-class object） |
| 反馈层（学习） | `find_precedents` 检索相似先例、追溯因果链 | 先例检索（precedent search）+ 因果分析 |

三层合起来：**本体让决策可记录，决策让判断可积累，先例让回路可学习。**

### 已建成哪一环，还差哪一环

如实说，这套方法把「观察 → 判断 → 决策 → 学习」的分析层闭环建成了；一条完整的回路还缺「行动 → 结果回传」的执行层闭环——把决策落地到真实业务系统、把对错写回来验证当初的判断。前者 Semantica 已覆盖，后者需要与业务系统打通。

这也是全文档集反复强调「溯源不可断、先冲突后合并、决策即一等对象」的原因：它们不是教条，而是让回路转起来的地基。
