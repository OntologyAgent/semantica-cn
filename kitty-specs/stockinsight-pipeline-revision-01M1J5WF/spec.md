# StockInsight 流水线最佳实践对齐修订

**Mission**: stockinsight-pipeline-revision-01M1J5WF | **类型**: software-dev | **日期**: 2026-09-03
**分支契约**: 从 `feature/stockinsight-raw-analysis` 切出 `feature/stockinsight-pipeline-revision`，PR 合回 main
**基准**: [本体建模-03-提示词与双模型协同](../../docs/best-practices/本体建模-03-提示词与双模型协同.md)（成熟方案，逐条落地；落地冲突时调整落地形态，方案缺陷则回写修订篇3——双向迭代）

## 一、背景与目标

上一使命（stockinsight-raw-analysis）完成 96 文件全量处理，实战审计暴露三层偏差：

1. **多语言**：披露易公告繁体与新闻简体同名分裂，88 组/182 实体重复（已用 OpenCC 兜底修复，但源头未治理）
2. **指代消解**：「本公司/本集团/发行人」自称未在抽取源头消解，91 条边挂假枢纽（已用 ALIAS+门禁兜底，源头未治理）
3. **偷工**：抽取无 Pydantic 硬校验（`json.loads` 手工容错）、双模型协同审计完全未做

本次以篇3 为基准修订处理方案（PLAN.md）与脚本：**语义判断在抽取源头由 LLM 完成**（自称替换、繁简统一、类型受控），**Pydantic 硬校验**拦截坏输出，**抽样双模型审计**四维把关，确定性代码只管机械转换与门禁。修订完成后全量重跑。

## 二、用户场景与验证

**主场景（按篇3 重跑）**：修订后的管线处理 96 文件——LLM 按四段式提示词抽取（自称已替换、简体统一、类型受控），输出经 `generate_typed(schema=…)` 字段级校验；抽样批次送审计模型四维审查，error 级问题批次回滚重抽；merge 重建 final，指代/繁简残留 0，图校验全过。

**场景二（审计回滚）**：审计发现某公告批次的财务数字与原文不符（error 级）→ 该批次作废重抽 → 复审通过 → 重抽与仲裁记录留档。

**场景三（处理方式确认）**：用户对照「处理方式清单」逐环节核查——每个语义判断环节都标注了 LLM 提示词位置，机械环节（id 折叠、校验、导出）标注确定性代码位置与理由；确认无一语义判断落在正则/字符串处理。

**边界与例外**：审计模型与生成模型同供应商时，用不同型号或独立 Prompt 扮演审计角色，并在清单中如实标注「非异构」局限。
